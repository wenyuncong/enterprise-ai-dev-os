# 2026-09-21 全 AI 开发操作系统项目扫描与交付生成审计

## 本轮结论

本方法论此前已经具备项目接入、技能候选隔离、复制预检、候选治理和基础知识索引，但架构扫描、12/13 步自动生成和知识中心图谱仍主要依靠人工解释。本轮补齐了一个通用、语言无关的生成闭环：

```text
项目扫描 -> Technology Profile -> Architecture IR
-> 13 步适用性计划 -> Task DAG -> 静态知识中心
```

源文档称为“12 步开发”，但运行时验证是单独的 Step 13。生成器保留完整 13 步，并对每一步输出 `applicable`、`not_applicable` 或 `needs_confirmation`，避免把不存在的数据库、前端、种子数据、租户同步或发布条件误判为已完成。

## 新增能力

- `scripts/py/architecture_delivery.py`
  - 只读扫描依赖清单、源文件、导入、常见 API 路由、SQL `CREATE TABLE`、测试文件和部署标记。
  - 输出语言无关 Architecture IR，节点和边带来源与置信度。
  - 生成 13 步交付适用性计划、依赖 DAG 和静态 HTML 知识中心。
- `skills/core/ai-architecture-knowledge-and-delivery/SKILL.md`
  - 明确图谱是发现证据，不是运行时权限、数据库真相、业务闭环或发布证据。
- `knowledge/architecture/`
  - 当前项目快照：118 个节点、334 条边、13 步计划、11 个 DAG 节点。

## 尚未自动化的边界

- 动态路由、运行时配置、真实数据库状态、权限和业务规则不能仅靠静态扫描确认。
- 自动生成计划不能替代产品目标、业务验收、破坏性操作确认、迁移授权和发布放行。
- 外部 GitHub 技能仍必须经过来源锁、许可证、兼容性、安全和所有者决策；本轮没有批量导入外部技能。
- 图谱应在源码、依赖、Skill 或脚本发生实质变化后增量刷新，而不是每次会话盲目全量重建。

## ERP 参考边界

云软 ERP 可作为采购、销售、库存、财务、主数据、权限、单据和审计等业务流程的参考来源，但不能把其某一种语言、框架或目录结构直接提升为通用方法论。通用核心应保持 Domain Model、Capability Model、Flow Model、Architecture IR 和 Evidence Contract；Java、Python、Node、Go、Rust、.NET 等通过适配器接入。
