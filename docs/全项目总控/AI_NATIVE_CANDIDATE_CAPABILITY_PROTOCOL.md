# 全 AI 原生候选能力评估与验证协议

> 版本：1.0
> 日期：2026-08-09
> 定位：全 AI 原生开发标准的准入协议。适用于网页结论、Skill、代码片段、工具输出、模型建议、第三方库、内部历史资产和候选原子。

## 1. 核心立场

候选能力的来源不是结论。

“可信”和“不可信”不是本协议的主分类。来源、作者、签名、引用、历史表现和供应链信息都可以进入评估，但它们只回答来源背景，不能自动回答“是否适合进入当前项目”。

真正的准入问题是：

```text
候选能力在当前项目、当前任务、当前架构、当前领域边界内，
是否合理、是否有收益、是否可验证、是否可回退。
```

## 2. 适用对象

- 网页、论文、论坛文章、开源仓库和产品文档。
- Skill、规则、模板、脚本和 MCP 工具定义。
- 代码片段、补丁、依赖库、容器镜像和模型输出。
- Agent 产出的方案、执行计划、测试建议和架构建议。
- 内部项目中待提炼或待迁移的实现、文档、脚本和流程。

## 3. 状态机

```text
discovered
-> scoped
-> evaluated
-> sandbox_validated
-> promoted

evaluated
-> retained
-> rejected
-> isolated
```

| 状态 | 含义 | 是否可正式执行 |
|---|---|---|
| `discovered` | 已发现，尚未确认用途 | 否 |
| `scoped` | 已绑定问题、项目和影响范围 | 否 |
| `evaluated` | 已完成适配评估 | 否 |
| `sandbox_validated` | 已在受控环境验证 | 仅限批准范围 |
| `promoted` | 已成为正式规则、Skill、原子或能力 | 是，受既有治理约束 |
| `retained` | 保留为参考，不进入正式能力 | 否 |
| `rejected` | 明确不适配当前目标 | 否 |
| `isolated` | 风险或未知影响未消除，隔离保存 | 否 |

## 4. 六维评估

| 维度 | 要回答的问题 |
|---|---|
| 目标契合 | 是否解决当前业务目标或工程问题？ |
| 架构契合 | 是否符合真相源、原子、编排、聚合接口、命令网关和 Host 边界？ |
| 领域契合 | 是否符合业务规则、权限、状态、数据和责任边界？ |
| 依赖与运维 | 是否引入不可接受的依赖、资源、许可、运维或锁定成本？ |
| 可验证性 | 是否能定义测试、API、浏览器、日志、数据或业务流证据？ |
| 可逆性 | 失败后是否能停止、隔离、回滚或补偿？ |

来源、签名、引用、许可证、SBOM 和历史表现可以作为辅助证据，但不得替代项目内评估和验证。

## 5. 最小准入记录

任何候选能力至少应形成：

```text
CandidateCapabilityEvaluation
  + DelegationGrant（如由 Agent 执行）
  + ExecutionAttestation（如发生验证或执行）
```

对应机器可读 Schema：

- `schemas/digital-life/candidate-capability-evaluation.schema.json`
- `schemas/digital-life/delegation-grant.schema.json`
- `schemas/digital-life/execution-attestation.schema.json`

## 6. 晋升门槛

候选能力仅在同时满足以下条件后才能晋升：

1. 已绑定明确问题、项目范围和非目标。
2. 已完成六维评估，并说明限制。
3. 已确认不会绕过真相源、命令网关、权限和证据边界。
4. 已完成与风险等级相称的受控验证。
5. 已记录版本、输入、执行人或 Agent、决策和证据。
6. 对高风险动作，已具备授权委托、确认、dry-run、回滚或补偿策略。

## 7. 审计原则

- 不因内容来自网页、第三方 Skill 或模型输出而自动拒绝。
- 不因内容来自内部资料、知名组织或历史项目而自动接受。
- 不把“参考”误写成“正式能力”。
- 不把一次成功验证夸大为通用正确性。
- 不把评估记录当成业务验收；最终业务验收仍由产品负责人完成。
