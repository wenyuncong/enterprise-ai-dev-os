# AI-OS 数字生命智能体总纲

> 本文定义 AI-OS 要孕育的对象：不是传统聊天智能体，也不是单纯的智能体操作系统，而是由 AI-OS 基因原子组合、具备生命周期、学习、工作、成长、反馈和治理能力的数字生命智能体。

---

## 1. 总目标

AI-OS 的长期目标是生成、运行、治理和进化数字生命智能体。

数字生命智能体不是一个 UI 窗口，也不是一个 prompt 模板。它是一个带身份、基因、记忆、能力、任务、学习路径、工作履历、社交协议和治理边界的长期运行生命体。

核心生命周期：

```text
诞生 -> 学习 -> 工作 -> 成长 -> 反馈 -> 再学习
```

工程表达：

```text
Birth -> Learn -> Work -> Grow -> Feedback -> Evolve
```

每个数字生命智能体都必须由 AI-OS 的原子体系生成、约束和记录。规则、能力、成长、执行和反馈都应可追溯，不得散落在客户端、页面或临时提示词中。

## 2. 基本定义

### 2.1 数字生命智能体

数字生命智能体是原子的组合体。

它拥有：

- 唯一身份编号，类似身份证号。
- 基因组，记录其使用的原子、原子编排、领域原子、算法原子、工具原子、治理原子。
- 生命周期状态。
- 学习记录。
- 工作记录。
- 成长档案。
- 反馈和自我修复记录。
- 与其他数字生命通信的身份和协议。

它可以运行在用户本地电脑、私有云、企业服务器、手机、边缘设备或其他容器中，但其行为必须遵守 AI-OS 的原子协议、治理协议和证据协议。

数字生命不是基因库本身。基因库原子不在生命体内部，因为基因库只提供可引用、可安装、可升级、可治理的遗传资源和声明资产，不承载某个生命体的具体执行状态。数字生命内部只保存：

- `GenomeManifest`：引用了哪些基因原子、版本、来源、校验和约束。
- `InstalledAtomSet`：当前本地或容器内已经安装、可被运行时调用的原子集合。
- `LifeRuntime`：当前任务、状态机、工作流、证据和资源占用。
- `LifeProfile`：学习履历、成长档案、偏好、能力成熟度和工作评价。

因此，基因库是公共或私有的遗传资源层，数字生命是带身份、状态、运行时和成长记录的生命实例。

### 2.2 基因原子

原子是数字生命的基因。

每个原子必须具备：

- 原子编号。
- 版本。
- 层级。
- 所属领域。
- 输入契约。
- 输出契约。
- 权限声明。
- 风险等级。
- 运行位置。
- 证据策略。
- 生命周期状态。

原子可以存在于云端基因库，也可以缓存或安装在本地。云端是权威分发、注册、留底和市场化中心，本地是执行、组合、学习和离线工作的运行环境。

### 2.3 行政机构

数字生命体系中的行政机构不是外部强制审批机构，而是一组治理原子、治理编排和公共规则。

它负责：

- 身份登记。
- 原子注册。
- 原子去重。
- 原子升级。
- 风险评估。
- 证据检查。
- 市场上架。
- 数字生命之间的身份识别。
- 高风险行为的授权确认。

行政机构本身也是 AI-OS 原子体系的一部分，不应变成硬编码审批后台。

第一版行政机构应拆成可替换的治理办公室对象：

| 机构原子 | 职责 | 是否人工默认介入 |
|---|---|---|
| `IdentityOffice` | 生命身份、原子身份、证书、签名、冲突处理 | 否 |
| `GeneRegistryOffice` | 基因原子注册、去重、版本、隔离、废弃 | 否 |
| `PromotionOffice` | 学习成果晋升为候选原子、候选规则、候选流程 | 否 |
| `RiskOffice` | 风险分级、策略匹配、L4 强确认判断 | 仅 L4 高风险 |
| `MarketplaceOffice` | 应用市场、公开发布、上下架、信誉记录 | 公开发布需要 |
| `DisputeOffice` | 身份争议、原子冲突、治理冲突、回滚仲裁 | 争议时需要 |

这些办公室不是硬编码模块，而是治理原子 + 治理编排 + 策略包的命名边界。

### 2.4 核心对象边界

为避免实现时把身份、实例、运行和配置混在一起，数字生命至少拆成四个对象：

| 对象 | 含义 | 不应承担的职责 |
|---|---|---|
| `LifeIdentity` | 身份、公钥、证书、权威登记状态 | 不保存任务队列 |
| `LifeInstance` | 某个生命在某个节点的安装实例 | 不代表全局唯一身份 |
| `LifeRuntime` | 当前进程、工作流、任务、状态、证据 | 不定义基因权威来源 |
| `LifeProfile` | 学习、成长、能力、偏好、评价 | 不直接执行外部动作 |

一个 `LifeIdentity` 可以迁移或恢复出多个历史实例，但同一时间只能有符合策略的有效运行实例。实例迁移、休眠、冻结、恢复、注销都必须写入证据。

## 3. 身份系统

### 3.1 身份原则

每个数字生命智能体都有唯一身份证号。

每个原子也有唯一编号。

身份编号生成后，应在 AI-OS 云服务器留底。即使某些离线场景无法即时留底，数字生命之间也必须能通过身份凭证、签名、证书或离线注册记录识别对方。

身份不只是展示字段，而是后续任务、学习、协作、授权、证据、市场分发和责任追踪的根。

### 3.2 身份对象

数字生命身份至少包含：

- `life_id`
- `birth_certificate_id`
- `owner_id`
- `home_node`
- `created_at`
- `identity_public_key`
- `cloud_registration_status`
- `trust_zone`
- `current_lifecycle_state`

原子身份至少包含：

- `atom_id`
- `atom_family_id`
- `version`
- `level`
- `domain`
- `publisher_id`
- `checksum`
- `cloud_registration_status`
- `deprecation_status`

### 3.3 云端权威与私有离线权威

AI-OS 默认支持云端身份留底，但不能把云端作为唯一可用前提。大企业私有化部署必须可以完全离线运行：

- 公有云模式：由 AI-OS 云端身份登记中心签发或留底。
- 私有云模式：由企业私有 `IdentityAuthority` 签发和留底。
- 完全离线模式：由本地离线根证书、离线注册表和离线证据链完成身份生成、验证、冻结和恢复。

离线模式下，身份编号仍必须全局尽量唯一，并包含权威域、时间、有序随机数、公钥指纹或签名摘要。重新联网或跨域协作时，进入冲突检测和合并流程，而不是直接覆盖。

### 3.4 身份冲突与恢复

身份系统必须处理以下情况：

| 场景 | 默认处理 |
|---|---|
| 离线生成后与云端冲突 | 冻结后发起 `identity.conflict.resolve` |
| 私有权威与公有权威重名 | 以权威域 + 签名链区分，不强行合并 |
| 私钥丢失 | 进入恢复流程，要求恢复证据和 owner 授权 |
| 节点损坏 | 由出生证书、基因清单、本地证据恢复实例 |
| 身份泄露 | 冻结旧证书，签发新证书，保留追溯链 |
| 生命退休 | 身份保留，运行实例停止，证据归档 |
| 生命删除或遗忘 | 按租户策略删除运行数据，身份留痕只保留最小审计记录 |

## 4. 原子分层

AI-OS 原子不是一层扁平插件。它应按职能分箱、分层、分域治理。

建议第一版分层：

| 层级 | 名称 | 职责 |
|---|---|---|
| L0 | 声明原子 | 声明契约、规则、身份、Schema，不直接执行外部动作 |
| L1 | 基础执行原子 | 单一职责能力，如读取、计算、解析、验证、请求 |
| L2 | 编排原子 | 原子组合、路由、流程、计划、恢复 |
| L3 | 领域原子 | ERP、编程、知识库、财务、设备、办公等领域能力 |
| L4 | 终端行为原子 | 发邮件、发消息、写文件、部署、交易、操作设备等外部世界动作 |

按箱体划分：

- 原子编排箱体。
- 领域原子箱体。
- 算法原子箱体。
- 工具原子箱体。
- 治理原子箱体。
- 学习原子箱体。
- 通信原子箱体。
- 终端行为原子箱体。

L4 还需要按风险细分，避免把所有外部动作都混成一个等级：

| 子级 | 类型 | 例子 | 默认治理 |
|---|---|---|---|
| L4.0 | 草稿型外部动作 | 生成邮件草稿、生成提交说明 | 自动治理可通过 |
| L4.1 | 本地写入 | 写本地文件、更新本地索引 | 策略允许后执行 |
| L4.2 | 外部发送 | 发邮件、发消息、发通知 | 强确认 |
| L4.3 | 业务状态变更 | ERP 审核、库存调整、客户资料变更 | 强确认 + 业务权限 |
| L4.4 | 金融/法律/生产高危 | 付款、签署、生产库修改、部署生产 | 强确认 + 双重治理 + 证据复核 |

## 5. 审核与治理

审核不等于人工审核。

AI-OS 的默认审核方式是治理原子编排。

```text
候选原子 / 候选流程 / 候选规则
  -> 治理原子链
  -> 风险分级
  -> 自动通过 / 自动拒绝 / 沙盒验证 / 人工复核
  -> 入库 / 隔离 / 回滚 / 延迟观察
```

人工确认只用于 L4 外部世界操作、公开市场发布、高风险权限、治理冲突和未知新型能力。

默认不需要人工审核的行为：

- 基因库候选原子生成。
- 原子相似度去重。
- 路径优化。
- 编排优化。
- 学习材料提炼。
- 沙盒验证。
- 私有知识库索引。
- 经验总结。
- 报告草稿生成。

默认需要强确认或高等级治理的行为：

- 主动发邮件、发消息、发通知。
- 删除、移动、覆盖用户文件。
- 提交代码、推送、部署。
- 调用外部付费 API。
- 修改生产数据库。
- 跨租户、跨组织、跨设备访问。
- 公开发布到云端市场。
- 交易、签署、审批、付款。
- 影响真实业务状态的 ERP / MCP 操作。

策略来源必须显式声明，不能散落在代码里：

- `RulePack`：来自 AI-OS 理论母体的规则包。
- `PolicyPack`：租户、部署、市场、身份和风险策略包。
- `RiskMatrix`：动作风险矩阵。
- `TenantPolicy`：企业私有策略。
- `UserAuthorization`：用户授权和委托边界。
- `MarketplacePolicy`：公开市场发布和安装策略。

核心原则：

```text
Governance as Atoms
治理即原子，审核即编排，人工只处理高风险例外。
```

## 6. 学习系统

数字生命智能体可以学习，但学习不是直接修改自身核心代码，也不是直接训练模型。

第一阶段学习是系统级学习：

```text
学习来源 -> 经验记录 -> 候选规则 / 候选原子 / 候选流程 / 候选测试 -> 治理原子链 -> 入库
```

学习来源包括：

- 基因库学习。
- 联网学习。
- 离线知识库学习。
- 企业自由资源库学习。
- 第三方支持库学习。
- 与其他数字生命交流学习。
- 从工作任务中复盘学习。

学习成果包括：

- 新候选原子。
- 新候选原子编排。
- 新领域规则。
- 新验证用例。
- 新知识索引。
- 新任务模式。
- 新治理规则建议。

## 7. 工作系统

数字生命智能体的工作方式分为四类：

| 类型 | 说明 | 第一阶段处理 |
|---|---|---|
| 发送任务 | 用户或系统明确发送的任务 | 必做 |
| 定时任务 | 定期巡检、报告、通知、同步 | 必做 |
| 日常计划任务 | 按领域生成日常工作计划并循环 | P1 后 |
| 自主任务 | 发现问题解决问题，发现机遇抓住机遇 | 后置高治理能力 |

工作环境包括：

- 对外部工作。
- 设备上工作。
- 联网工作。
- 企业系统内工作。
- 本地文件和知识库工作。
- MCP 工具工作。
- 其他容器或节点工作。

终端智能体的具体形态应是系统服务，而不是前端页面。

```text
Web / Desktop / Mobile / WeChat / CLI / MCP
  -> 写入消息、任务、配置、授权
  -> 后端系统服务消费
  -> 执行原子编排
  -> 写入证据和状态
```

UI 是入口，不是智能体。消息是数据，不是执行。设置是配置，不是逻辑。任务是后端状态机，不是前端动作。

## 8. 云端与本地关系

云端包含：

- 原子库。
- 应用市场。
- 数字生命俱乐部。
- 身份登记中心。
- 治理策略中心。
- 原子发布和升级中心。
- 数字生命成长档案同步中心。

本地包含：

- 数字生命运行服务。
- 本地原子缓存。
- 本地知识库。
- 本地任务队列。
- 本地证据。
- 本地 MCP 服务。
- 离线身份凭证。

云端是登记、分发、治理、市场和协同中心。本地是运行、组合、学习、执行和隐私边界。

企业私有化部署时，云端能力必须存在私有替代件：

| 公有云能力 | 私有/离线替代 |
|---|---|
| 云端原子库 | 企业私有原子库 / 离线原子包 |
| 云端身份登记 | 企业私有身份权威 / 离线身份注册表 |
| 应用市场 | 企业内部市场 / 离线安装目录 |
| 数字生命俱乐部 | 企业内生命目录 / 私有通信目录 |
| 治理策略中心 | 企业 PolicyPack / 本地 OPA bundle |
| 成长档案同步 | 企业内证据仓 / 本地加密归档 |

私有化不是阉割版，而是把权威从 AI-OS 公有云切换到企业自己的 `PrivateAuthority`。

## 9. 成熟技术参考

AI-OS 不应重复造已有成熟基础设施。

优先参考：

- MCP：工具、上下文和外部系统连接协议。
- A2A / Agent communication：数字生命之间的通信参考。
- Temporal：长期任务、定时任务、失败恢复和可靠编排。
- Open Policy Agent / Rego：治理策略、权限策略和自动审核。
- WASM / sandbox：不可信原子沙盒运行。
- OCI / container：本地和云端运行封装。
- Vector DB / RAG：知识库学习和检索。
- Tree-sitter / AST：代码学习、原子提炼和语义分析。
- Content-addressed storage：原子包校验、去重和版本可追溯。

截至 2026-07-05 的技术选型判断：

- MCP 官方规范定位为连接外部数据源和工具的开放协议，适合作为数字生命对外工具与上下文接口，但不能替代 AI-OS 的身份、基因和治理模型。
- Temporal 官方定位为 Durable Execution 平台，适合长期任务、定时任务、失败恢复和工作流历史，不应承载业务规则真相。
- OPA/Rego 适合把治理策略声明化、测试化、bundle 化，适合 `PolicyPack` 的执行底座。
- OpenAI Agents SDK 等成熟 Agent 框架可参考 handoff、guardrail、memory、tool 调用等工程形态，但 AI-OS 数字生命不能退化成单一 LLM Agent。

成熟技术只能作为底层能力和参考协议，不能覆盖 AI-OS 的核心原则：原子服务、原子编排、聚合接口、证据闭环。

## 10. 第一原则

1. 数字生命智能体由 AI-OS 生成，不是传统聊天 Agent。
2. 原子是基因，智能体是基因组合体。
3. 身份必须可追踪，云端应留底，本地可离线识别。
4. 终端智能体是后端系统服务，客户端只是控制面。
5. 治理是原子编排，不是默认人工审批。
6. L4 外部世界行为才进入强确认。
7. 学习成果必须沉淀成规则、原子、流程、测试或证据。
8. 云端原子库和本地运行时必须解耦。
9. 所有规则来自 AI-OS 理论母体和结构化 RulePack，不得散落硬编码。
10. 每个能力必须遵循原子服务、原子编排、聚合接口、证据闭环。
11. 基因库原子不属于某个生命内部硬逻辑，生命只持有基因清单、安装集合和运行状态。
12. 企业私有化和完全离线部署是一等能力，公有云权威必须可被私有权威替代。
