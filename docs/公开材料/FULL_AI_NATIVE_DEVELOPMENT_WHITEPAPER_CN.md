# 全 AI 原生开发白皮书

> 版本：Draft 1.1  
> 日期：2026-08-09  
> 用途：企业客户、技术论坛、投资人、合作伙伴沟通。  
> 公开边界：本文为脱敏外发稿，不包含客户名称、私有仓库路径、本机路径、内部运行证据或未经验证的固定收益数字。

## 0. 摘要

全 AI 原生开发不是让软件项目里堆叠更多大模型、更多智能体或更多提示词。它是一套面向 AI 协作时代的软件开发标准：让软件系统从设计之初就具备可被 AI 理解、调用、治理、验证和进化的结构。

这套标准的核心价值不是替代人，而是重新分工：

- 人负责想法、目标、业务判断和最终验收。
- AI 与智能体负责代码、方案、创意实现和重复性工程执行。
- 采用本方法论的目标项目后端和 runtime 负责真相、权限、状态、证据和风险边界。本仓库提供方法论和门禁，不提供通用 runtime。
- 门控、测试和回归机制负责把“看起来完成”变成“可以复核”。

因此，全 AI 原生开发的目标不是更快生成代码，而是让 AI 生成的代码、流程和能力可以进入真实业务系统，并保持可控、可验、可演进。

## 1. 为什么普通 AI 编程会失控

AI 编程工具可以快速生成代码、页面、接口、文档和测试。但在复杂业务系统中，速度并不等于交付能力。缺少统一标准时，常见问题会反复出现：

- 文档很多，但没有统一真相源，AI 不知道哪个规则优先。
- 代码增长很快，但架构边界不清，登录、权限、状态、数据回写等基础能力反复出错。
- 前端、后端、脚本、文档各自生成，最后彼此不一致。
- AI 根据旧上下文、局部文件或错误记忆直接修改代码，导致问题被放大。
- 功能看似完成，但缺少可复核的测试、API、浏览器、日志或业务流证据。
- 多个 AI 工具协作时，每个工具都有自己的上下文和习惯，项目规则无法稳定继承。

这说明企业级 AI 开发的核心问题不是“AI 会不会写代码”，而是“AI 在什么结构内写代码、调用能力、留下证据、接受治理”。

## 2. 核心定义

全 AI 原生开发是一套让软件系统从设计之初具备 AI 协作能力的开发标准。它要求系统中的业务事实、服务能力、编排流程、操作入口、界面承载、运行时治理和验证证据都可以被 AI 读取、解释、调用、审计和持续改进。

简化定义：

```text
全 AI 原生开发 =
让软件生来具备可被 AI 理解、调用、治理、验证和进化的结构。
```

它不是：

- 不是简单使用 AI IDE。
- 不是提示词工程的堆叠。
- 不是让智能体直接绕过业务系统执行动作。
- 不是把所有代码都交给大模型自由发挥。
- 不是宣称 AI 可以替代产品负责人、业务负责人或最终验收人。

它是：

- 一套开发标准。
- 一套架构约束。
- 一套治理机制。
- 一套证据闭环。
- 一套让 AI 能稳定参与真实软件交付的工程方法。

## 3. 认知演进：解释、标准、发挥

全 AI 原生开发的认知演进可以概括为三步：

```text
解释 -> 标准 -> 发挥
```

第一阶段是解释。人把业务想法、目标、例子、截图、验收结果交给 AI，AI 尝试把它解释成需求、任务和代码。

第二阶段是标准。系统把解释过程沉淀为可复用的规则、技能、文档结构、注册表、runtime 契约和验证门禁。AI 不再靠临时理解工作，而是在结构内工作。具体 runtime 机制由采用方项目实现，本仓库不宣称已经提供通用 runtime。

第三阶段是发挥。当标准稳定后，AI 与智能体获得更大的发挥空间。它们可以实现代码、生成方案、编排流程、提出优化建议，但所有动作都经过注册、权限、状态、证据和验收。

真正的关键是：标准不是为了限制 AI，而是为了让 AI 在更大的空间内稳定发挥。

## 4. 参考架构

全 AI 原生开发建议将能力链路拆成两条主线：后端真相链和前端承载链。

后端真相链：

```text
truth
-> atomic service
-> orchestration
-> aggregate interface
-> command gateway
-> adapters
-> Host / AI / MCP / OpenAPI
```

前端承载链：

```text
runtime / field truth
-> UI atom
-> UI orchestration
-> standard template
-> Host page
```

这两条链路的关键点是：业务真相、字段真相、权限真相、状态迁移和写入动作必须由后端和 runtime 管理。Host 页面、App、AI 客户端、MCP 客户端和 OpenAPI 客户端只加载、展示、收集输入、请求命令和展示反馈，不应成为第二套业务逻辑。

### 4.1 从 AI 辅助开发到 AI 原生开发

豆包白皮书草稿提出了一个有价值的叙事框架：传统开发、AI 辅助开发和全 AI 原生开发的差异，不只是“谁来写代码”，更是责任边界和验证结构的差异。

| 维度 | 传统开发 | AI 辅助开发 | 全 AI 原生开发 |
|---|---|---|---|
| 人的主要角色 | 代码生产者 | 代码审核者和修改者 | 目标、治理和最终验收者 |
| AI 的主要角色 | 不存在或局部工具 | 代码和方案生成器 | 受规则、能力注册和验证门禁约束的执行者 |
| 质量保证 | 人工测试和审查 | 人工审查加局部自动化 | 可复核的测试、运行时、业务流和发布证据 |
| 知识沉淀 | 个人经验和文档 | Prompt 与聊天记录 | 规则、Skill、模板、审计脚本和回归记录 |
| 失败修复 | 人定位和修复 | AI 提建议，人执行 | 在授权边界内由 AI 执行，人处理业务取舍和高风险确认 |

这里的“AI 原生”不是承诺人完全退出，也不是承诺系统可以无条件自治。它表示：系统从架构、能力注册、命令入口、Runtime 和证据链开始，就为 AI 的可理解、可调用、可治理和可验证而设计。

### 4.2 五层 Skill 操作系统

本方法论的 Skill 体系可以用五层结构表达：

```text
Layer 0: Classification  -> 这是什么项目，质量目标是什么
Layer 1: Routing         -> 应加载哪些规则和技能
Layer 2: Decomposition   -> 如何拆成安全的执行批次
Layer 3: Execution       -> 如何实现、测试和验证
Layer 4: Evolution       -> 如何把重复经验升级为长期能力
```

| 层 | 主要职责 | 当前方法论对应 |
|---|---|---|
| 分类层 | 判断项目来源、质量目标、部署目标和规模 | `ai-project-classifier` |
| 路由层 | 选择主责 Skill、首读规则、前置检查和执行顺序 | `ai-rule-dispatcher` |
| 分解层 | 冻结范围、标记依赖、定义批次和验收证据 | `ai-task-decomposer` |
| 执行层 | 承载架构、治理、技术栈和平台能力 | Core、Governance、Tech、Platform Skills |
| 进化层 | 审计 Skill 健康度，提炼规则、测试和新 Skill | `ai-skill-evolver`、`ai-skill-governor` |

五层结构的价值不是增加文档数量，而是把“该做什么、由谁做、如何证明、如何复用”从一次性对话中抽离出来，变成项目可以重复运行的系统能力。

### 4.3 受治理的自治闭环

```text
任务输入
  -> 项目分类
  -> 规则路由
  -> 批次分解
  -> Skill 执行
  -> 测试与运行时验证
  -> 业务闭环与发布审计
  -> 文档回写与 Skill 进化
```

自治闭环的边界必须清楚：

- AI 可以负责需求分析、方案生成、实现、测试补充、证据整理和经验提炼；
- 目标项目 Runtime 负责真相、权限、状态、风险、审计和执行边界；
- 人负责目标、业务政策、优先级、重大取舍和最终业务验收；
- 删除、数据库迁移、生产发布、跨租户操作等高风险动作仍需明确授权和恢复路径。

### 4.4 资格与成熟度不能只看“能力存在”

能力进入注册表、菜单或页面，只能说明它存在，不能说明它已经可交付。交付资格采用 Q0-Q3：

| 资格 | 含义 | 最低证据 |
|---|---|---|
| Q0 | 能力存在 | 源码、注册表或路由检查 |
| Q1 | 基线对齐 | 参数、权限、状态、配置和依赖回读 |
| Q2 | 技术可执行 | Provider、编排、唯一副作用路径、审计和权威回读 |
| Q3 | 业务已闭环 | 真实业务验收、跨端/运行时、对账和发布证据 |

同时使用能力成熟度链：

```text
registered
  -> configured
  -> authorized
  -> provider-covered
  -> runtime-executable
  -> business-closed
```

因此，页面打开、HTTP 200、健康检查、CI 通过或本地提交，都不能单独证明 Q3 或 `business-closed`。

### 4.5 多 Agent 和多机协同

当任务规模扩大时，总控对话可以通过任务清单、批次契约、依赖关系和独立工作区协调多个 AI 会话。安全边界包括：

- 每个批次必须有明确的写入范围、非目标、公开测试接缝和证据要求；
- 不同批次优先使用不重叠的领域和文件边界；
- 共享总控文档只记录状态、决策和证据，不替代真实代码、数据库或 Runtime 真相；
- 合并前必须进行范围检查、标准/真相复核和产品验收复核；
- 多机协同是执行组织方式，不是业务闭环或发布证据本身。

## 5. 核心对象

| 对象 | 核心职责 |
|---|---|
| 真相源 | 定义业务事实、字段、权限、状态和数据归属 |
| 原子服务 | 承载最小稳定业务能力 |
| 原子编排 | 把多个原子组合成业务流程 |
| 聚合接口 | 向 Host、AI、MCP 提供可理解的业务能力画像 |
| 命令网关 | 作为唯一动作入口，处理权限、状态、幂等、审计和风险 |
| 注册表 | 登记能力、版本、状态、提供方、权限和可调用边界 |
| Host | 加载和展示聚合接口，收集输入并调用命令网关 |
| 目标项目 Runtime | 执行采用的标准、维护真相、记录证据、管理风险和演进 |
| 证据闭环 | 用测试、日志、API、浏览器和业务流证明结果 |

这些对象共同构成一个面向 AI 的软件操作结构。AI 不需要猜测系统能力，而是通过注册表、聚合接口和 runtime profile 理解当前系统能做什么、不能做什么、为什么。

## 6. AI 治理不是限制，而是放大空间

传统语境中的治理常被理解为限制、审批和阻碍。但在全 AI 原生开发中，治理的目的不是压制 AI，而是让 AI 可以在更大的空间中安全发挥。

治理通过以下方式扩大 AI 的可用范围：

- 用规则说明项目边界，让 AI 不必每次重新猜测。
- 用 Skill 封装高频任务，让 AI 能复用成熟路径。
- 用注册表告诉 AI 哪些能力存在、由谁提供、是否可执行。
- 用命令网关保证所有动作通过同一入口。
- 用候选能力评估把外部知识、Skill 和工具输出转化为可验证输入，而不是直接指令。
- 用 runtime 记录状态、权限、证据和风险。
- 用门控脚本和测试把经验转成可复核标准。
- 用文档回写和技能进化把重复问题沉淀为长期能力。

因此，治理的本质是：给 AI 定义一个可发挥、可追踪、可恢复、可升级的空间。

### 6.1 评估与验证优先于来源标签

网页、Skill、工具输出、模型建议、代码片段和第三方能力，不应只被粗暴划分为“可信”或“不可信”。来源信息有价值，但它只是证据之一，不能替代对当前项目的判断。

真正的问题是：这项候选能力进入当前项目后，是否解决真实问题，是否符合架构和领域边界，是否引入不可接受的数据、依赖、成本或维护风险，是否能够在受控范围内验证，失败后是否可以退出或回退。

因此，全 AI 原生开发采用的不是“来源标签优先”，而是：

```text
候选输入
-> 项目适配评估
-> 受控验证
-> 证据记录
-> 晋升、保留、拒绝或隔离
```

## 7. 人、AI、Runtime 的分工

全 AI 原生开发不是“人退出开发”，而是让人从代码细节中上移到意图、业务判断和验收。

| 角色 | 负责 | 不负责 |
|---|---|---|
| 人 | 目标、业务结果、优先级、取舍、最终验收 | 手工定位所有代码、重复执行机械验证 |
| AI / 智能体 | 需求分析、方案生成、代码实现、测试补充、文档提炼 | 擅自定义业务政策、绕过治理执行高风险动作 |
| Runtime | 真相、状态、权限、证据、风险、执行边界 | 替代人的商业判断 |
| 门控 / 测试 | 可复核证据、回归保护、发布前检查 | 替代真实业务验收 |

这套分工让非程序员也可以主导复杂软件交付：人不必亲自写代码，但必须清楚自己要什么、接受什么、不能接受什么。

## 8. 来自复杂 ERP 实战的启示

全 AI 原生开发标准来自复杂企业业务系统的长期实践。ERP 是天然的高压场景：它包含登录认证、权限、多租户、字段体系、采购、销售、库存、资金、审批、消息、打印、报表、版本、发布和回退。仅靠“让 AI 多写代码”无法稳定交付这样的系统。

实践中的关键启示包括：

- 前端只负责加载和展示，业务计算、权限、状态和写入必须由后端和 runtime 决定。
- 字段、页面、按钮、动作、权限不能散落在多个页面中，应由字段包、业务画像、注册表和 runtime profile 提供。
- 可执行动作不能因为界面上有按钮就可执行，必须通过命令网关进行状态、权限、幂等和审计检查。
- 聚合接口应向 Web、App、AI、MCP 和 OpenAPI 提供同一份能力画像，减少多端重复逻辑。
- 发生重复错误后，应升级规则、Skill、脚本、测试或文档，而不是只在一次对话中修补。
- 删除、迁移、发布、数据库变更、生产动作等高风险操作必须有明确边界、证据和确认机制。

这些实践说明，全 AI 原生开发不是理论装饰，而是从真实业务压力中反向提炼出来的工程标准。

## 9. 商业价值

全 AI 原生开发的商业价值不应被表述为固定比例的效率提升，而应表述为可验证的方向性收益：

- 减少重复解释：项目规则、Skill 和文档结构让 AI 更快进入上下文。
- 减少返工：门控、测试、运行验证和回归规则在更早阶段发现问题。
- 降低人员依赖：知识不只停留在个人脑中或聊天记录里，而是沉淀为标准资产。
- 支持多端复用：Web、App、AI、MCP 和 OpenAPI 共享后端聚合接口和命令网关。
- 提高交付可审计性：每个关键动作都能留下证据、状态和责任边界。
- 支持持续进化：重复问题可以升级为规则、Skill、脚本、测试和 runtime 能力。

这类价值可以通过确认轮次、返工次数、门控通过率、运行验证覆盖、回归缺陷数量、交付周期和知识复用情况来衡量。

## 10. 边界与非主张

为了保持可信，公开表达应避免以下误解：

- 不宣称 AI 可以完全替代人类产品判断。
- 不宣称零缺陷、固定节省比例或固定通过率。
- 不把未来自治智能体或“数字生命”概念表述为本仓库已经实现的能力。
- 不把训练自有大模型作为当前标准的必要条件。
- 不把特定工具、模型或供应商作为标准前提。
- 不把大型 ERP 私有细节、客户数据、本机路径或未脱敏证据对外发布。

正确表述应是：

```text
全 AI 原生开发是一套工程标准。
它让 AI 在可治理结构内发挥能力，而不是让 AI 无边界地替代所有角色。
```

## 11. 路线图

全 AI 原生开发可以分阶段落地：

| 阶段 | 目标 |
|---|---|
| S0 人工辅助 | 使用 AI 工具生成代码和文档，但缺少统一标准 |
| S1 规则化 | 建立项目规则、目录边界、开发顺序和基础验证 |
| S2 Skill 化 | 把高频任务沉淀为可复用 Skill、模板和检查脚本 |
| S3 架构原生 | 建立真相源、原子服务、编排、聚合接口、命令网关和 Host |
| S4 Runtime 治理 | 由项目 Runtime 管理权限、状态、证据、风险和多端调用 |
| S5 可进化系统 | 重复问题自动或半自动沉淀为规则、原子、测试、Skill 或治理策略 |

这条路线不要求一开始就建设完整自治 runtime 或大模型训练体系。对多数团队而言，先完成 S1 到 S3，就能建立有用的受治理交付基础。S4 和 S5 需要项目自身的 runtime 与证据，不会因为安装本仓库而自动获得。

## 12. 对外一句话

> 全 AI 原生开发不是让 AI 多写代码，而是用标准化的软件结构，让 AI 能稳定理解、调用、治理、验证和进化真实业务系统。

## 13. 结论

AI 时代真正缺的不是代码生成器，而是让 AI 生成的代码进入真实业务系统后仍然可控、可验、可演进的开发标准。

全 AI 原生开发的关键不是“AI 更强”，而是“标准更清楚”。标准越清楚，AI 的发挥空间越大；证据越完整，系统越能持续演进；runtime 越稳定，AI 越能安全进入真实业务。

最终目标不是让人被替代，而是让人从重复工程细节中释放出来，把注意力放在想法、业务结果、审美、取舍和验收上。
