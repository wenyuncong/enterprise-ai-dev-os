# Token Cost Model and Industry Benchmark for Full AI Development (v1.0)

# 全 AI 开发 Token 成本模型与行业对标（v1.0）

- 作者：文云聪（Yuncong Wen），成都云软科技有限公司
- 日期：2026-10-12
- 数据窗口：2026-09-01 ~ 2026-10-12（会话按开始日归集，有效开始日至 10-05）
- 许可：随仓库采用 Apache License 2.0
- 状态：**描述性实测（descriptive observations），非随机对照、非因果增量**

> 一句话结论：在一次"人不写、不审、不改一行源码"的全 AI 开发实践中，我们观测到 **99.6% 的 token 成本发生在输入（上下文）侧**、缓存命中达 **85.6%（近期 99%）**、典型（中位）会话规模随方法成熟下降约**两个数量级**；对照 2026 年公开行业数据，真正的分水岭不是模型单次准确率（已达 96%+），而是**成本治理与生产可靠性**——这正是本方法论所系统化的部分。

| 项 | 值 |
|---|---|

| 日期范围 | 2026-09-01 ~ 2026-10-05 |

**为什么没有"用 vs 不用"的对照**：本地用量数据只覆盖方法论成型之后，不存在"不使用方法论"的历史对照；用户决策不做前瞻 A/B。因此本文报告的是"使用之后的成本结构"与"随成熟的纵向变化"，**不声称相对基线省 X%**。

## 2. 实测成本结构

| 参数 | 实测值 | 占比/口径 |
|---|---|---|
| 输入 token | 10,340,512,271 | 占总量 **99.6%** |
| └ 缓存输入 | 8,850,160,534 | 占输入 **85.6%** |
| └ 非缓存输入 | 1,490,351,737 | 占输入 14.4% |
| 输出 token | 38,801,720 | 占总量 0.37% |
| └ reasoning | 10,067,092 | 占输出 25.9% |
| 会话规模 中位 p50 | 32,112 | 典型会话 |
| 会话规模 均值 | 10,096,600 | 为中位约 314 倍（长尾） |
| p90 / p99 / max | 1,204 万 / 2.03 亿 / 9.37 亿 | 高度长尾 |

会话规模直方图：10k–50k **606** 个；50k–200k 105；200k–1M 62；1M–10M 142；10M–100M 92；**>100M 21**。

按项目（token 前 3）：ERP 主仓 `gerp-enterprise-mainline` 281 会话 / **94.70 亿（约 91%）**；`ai-os` 87 会话 / 6.15 亿；本方法论仓 16 会话 / 1.44 亿。

**三个结构性结论：**
1. **成本 99.6% 在上下文，不在生成**。降本核心是上下文治理与缓存，而非"少写代码"；产出/输入比仅约 0.38%，符合"充分理解大上下文后做小而精准修改"的最小改动原则。
2. **高度长尾**：少数超长主会话吞掉绝大部分 token，而 606 个小任务每个约 3 万。
3. **缓存是已兑现的最大节省**：全局 85.6%、后期 99% 的输入命中缓存（缓存单价通常显著更低，具体倍数依供应方定价，本文不内置价格）。

## 3. 纵向效果（按周，描述性）

| 周 | 会话数 | 调用 | 总 token | **会话中位 token** | 缓存命中% |
|---|---|---|---|---|---|
| W36 | 102 | 8,396 | 51.2 亿 | 2,894,410 | 88.2 |
| W37 | 182 | 8,909 | 35.7 亿 | 4,464,768 | 82.0 |
| W38 | 59 | 4,136 | 11.3 亿 | 692,289 | 80.1 |
| W39 | 581 | 811 | 0.64 亿 | **31,666** | 73.9 |
| W40 | 95 | 2,837 | 3.21 亿 | **34,095** | **98.7** |
| W41 | 9 | 1,280 | 1.79 亿 | 19,230,144 | 99.3 |

**可读出的观测（实测）**：
1. 典型（中位）会话规模从 W36–W37 的约 289–446 万，降到 W39–W40 的约 3.2–3.4 万，约为原来的 **1/90 ~ 1/130（约两个数量级）**。
2. 缓存命中率从 W38 低点 80.1% 升至 W40–W41 的 98.7%–99.3%。
3. W39 起进入"小批快闭环"：581 个会话仅 0.64 亿 token，对应任务契约 + 门控 + 任务分解的工作模式。

**诚实声明**：该纵向变化混杂了**工作模式**（早期少数超长主会话连续推进 → 后期大量短任务会话）与任务类型差异，**不是随机对照实验**；中位数口径不被少数超长会话拉偏，方向稳健。W41 仅 9 个会话且含超长会话，样本过小、中位回升不具代表性。

## 5. 对标解读：旧尺子与新分水岭

1. **"单次准确率"这把尺子正在失效**：裸模型已普遍 96%+，但行业一致发现这**换不来生产可靠**（46% 上线即败、74% 需返工、43% 需手工调试）。
2. **2026 年真正的分水岭是成本治理与生产可靠性**：研究实锤 harness 选择可造成约 40 倍 token 差，而通过率几乎不变——即"怎么组织 AI 干活"比"模型本身"更决定成本与结果。
3. **本方法论的增量位置**：记忆/契约降返工、固定上下文拿高缓存、网关 + 门控在交付前拦截、MD 总控杜绝多机重复——系统化地补上了行业最缺的两块。其结果级证据是：**人零写/审/改，却有生产客户付费使用、黄金链路真机闭环（137 个 Bug 全关）**，跨过了 SWE-bench 到生产之间那道行业公认的鸿沟。

**评级（明确，标注证据强度）**：

| 维度 | 评级 | 证据强度 |
|---|---|---|
| 成本/效率 | 好，领先 | 强（机制对标 + 99% 缓存 + 纵向约 100 倍） |
| 准确性/可靠性 | 好 | 结果级强（生产付费、真机闭环）；缺缺陷率直接埋点 |
| 创新性/独特性 | 好，稀缺 | 强（全 AI、人零代码、长周期、生产付费 + 方法论/架构/系统三层沉淀） |

## 6. 诚实边界与威胁

- **无对照组**：纵向趋势不是因果增量；"约 100 倍"是同一项目不同周的中位会话规模对比，且混杂工作模式变化。
- **任务粒度不可直接相比**：本文"会话"与行业"任务"口径不同（一个任务可能含多个会话），故不写"比行业省 130 倍"。
- **豆包侧缺失**：豆包 GUI 会话在本地 IndexedDB（Chromium LevelDB、受锁、私有编码），**本地不记录 token 用量**，无法像 Codex 精确并表；豆包侧用量在服务端。
- **缺陷率/一次通过率精确百分比尚缺**：网关 ALLOWED 分母与质量埋点刚补齐，需约 4 周、≥200 事件的测量窗口。
- **金额不内置**：仅在显式传入单价时估算。
