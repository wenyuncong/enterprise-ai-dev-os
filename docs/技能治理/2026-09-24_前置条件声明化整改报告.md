# 技能前置条件声明化整改报告（2026-09-24）

> 承接《全量 264 技能逐篇语义审查表》结论：语义层零 FAIL，但 63 篇技能因依赖运行时前置条件（外部 CLI / 项目上下文 / 路径变量）在豆包等宿主中“可读不可执行”。本次落地整改方案 1——**前置条件声明化**，让技能可用性在“加载前即可判定”。

## 一、整改目标

把每个技能的运行时前置条件以**机器可读**方式写入 frontmatter `metadata.requires`，使宿主（含豆包 app 电脑客户端）在加载/路由技能前即可判断：需要哪些外部命令（bins）、环境变量（env）、第三方库（libs）、路径变量（path-vars），以及作用域 scope。缺失前置条件时明确报“未提供该命令/环境”，而非静默降级为“加载不了”。

## 二、声明规范（skill-requirements/v1）

```yaml
metadata:
  requires:
    bins: [lark-cli]          # 外部可执行命令
    libs: [python-docx]       # 第三方语言库
    env: [CNB_TOKEN]          # 所需环境变量
    path-vars: ['${CLAUDE_SKILL_DIR}']  # 路径变量
    scope: runtime            # universal | project | runtime
    declared-by: enterprise-ai-dev-os
```

| scope | 含义 |
| --- | --- |
| universal | 纯提示词/方法论，技能内 references 自足，任何宿主可读即可执行 |
| project | 需特定项目上下文（GERP / ai-os 代码库、项目脚本、项目数据） |
| runtime | 需宿主运行时提供外部命令/服务（CLI、MCP、飞书、检索工具、本地生成能力） |

## 六、豆包 app 电脑客户端 + 豆包模型匹配

- **验证对象**：本次 63 篇运行时技能即豆包 app 电脑客户端实际加载的 `.skills` / `.user_skills` 库；补齐后 frontmatter 为合法 YAML，`name` / `description` 与 `metadata.requires` 结构完整，可供豆包模型在技能路由（按 description 语义匹配）与加载前可用性判定使用。
- **匹配机制**：豆包模型按 `description` 做技能语义匹配 → 命中后读取 `metadata.requires`，据此判定 bins/env/scope 是否满足；不满足时可明确反馈缺失项（例如“需 lark-cli，当前未提供”），把“加载不了”转化为“可定位的前置条件缺口”。
- **验证边界（据实）**：本次在文件层 / YAML 层完成校验（合法、自洽、字段一致、正文无损）；豆包 app 内的实际技能路由与命令执行属客户端/服务端运行时行为，需客户端重新加载该技能库后确认。
