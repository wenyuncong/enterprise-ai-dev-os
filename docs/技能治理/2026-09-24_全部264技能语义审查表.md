## 二、对“豆包/国产模型技能加载”问题的答复

1. **方法论能检测、且已检测出该问题的结构**：`scan_skill_health.py`（commit `509f50c`/`752e409`）已把技能体检从“文件是否存在”升级为“依赖工具是否安装、是否在 PATH、是否需项目上下文”，并新增强制 `KNOWN_INSTALL_LOCATIONS` 探测（codex/flutter/playwright 已装不在 PATH 均实测命中）。本次语义审查进一步补上机扫测不到的软伤维度（指令自相矛盾/步骤歧义/能力不符），结论：**语义层零 FAIL**。
2. **真正的缺口是运行时适配层，不是技能内容**：63 篇可执行性受限的技能几乎全部指向同一类问题——技能正文引用了外部可执行程序或项目内脚本，而豆包智能体未注册/未提供这些命令。ChatGPT（Claude Code / Codex 类）能“像跑程序一样跑技能”，是因为宿主把技能目录挂进了 agent 的运行时路径并可执行 shell；豆包若以纯对话/受限沙箱承接，同一份技能就退化为“可读不可执行”。
3. **整改方向（已并入方法论）**：a) 技能前置条件声明化——frontmatter 增 `metadata.requires.bins` 与 `env`，让宿主在加载前即可判可用性；b) 运行时网关——把 `lark-cli`/`mediakit-cli`/`cnb` 等封装为宿主可调用的统一命令网关，缺失即明确报“未提供该命令”而非静默降级；c) 上下文判定——把“仅 GERP/ai-os 内可执行”的技能标注项目作用域，跨项目时路由到通用替代。
