# 11 — Universal Architecture and Governance Pattern Library | 通用架构与治理模式库

> **Part of**: Enterprise-Grade Full AI Development Methodology
> **Prerequisites**: 00_核心方法论白皮书, 01_Skill体系分层架构
> **Scope**: Language-neutral, project-neutral, business-neutral. Every pattern below is stated only in terms of layers (presentation / orchestration / persistence), data spaces, records, and control flow. No programming language, framework, product, project, or business domain is named. Stack-specific realizations belong to the optional adaptation layer and are never part of this library.

---

## 0. How to Use This Library | 如何使用本库

Each pattern has four parts:

- **Problem** — the recurring engineering symptom, independent of any technology
- **Pattern** — the structural response
- **Rules** — the non-negotiable constraints that make the pattern work
- **Acceptance** — what must be proven before work using the pattern is called done

A pattern is evidence-backed: it was extracted from concrete delivery work, then generalized by removing every language, project, and business reference. Do not reintroduce such references when applying it.

# Part I — Architecture Patterns for Partitioned Delivery | 分区交付架构模式

## 1. Zero-Disruption Introduction of an Optional Dimension | 可选维度的零扰动引入

**Problem**
A new partitioning dimension (for example, ownership by an organizational unit) must be added to a working system without destabilizing existing tenants, existing records, or existing workflows. A big-bank rewrite risks regressions across every existing flow.

**Pattern**
Introduce the dimension behind a tenant-level switch that is **off by default**, and carry the dimension on nullable fields. When the switch is off, the system behaves identically to before — no new filters, no required fields, no visible change. Existing rows keep a null dimension, which explicitly means "default / shared".

**Rules**
- Every write path checks the switch first; when off, the dimension is neither required nor defaulted to a fabricated value.
- The switch is tenant-scoped, so each tenant can adopt the dimension independently.
- Null on historical rows is a defined semantic, not an unknown state.
- No parallel data model is created; the dimension extends the existing model.

**Acceptance**
End-to-end proof in both states: with the switch off, existing flows produce byte-identical behavior and responses; with it on, the new filters and required-dimension rules work, and rows with null and rows with an explicit dimension coexist correctly.

## 2. Idempotent Unit Initialization and Master-Data Distribution | 单元初始化与主数据下发幂等

**Problem**
A unit that needs an independent working set (its own records, its own copy of controlled master data) must be initialized inside the same physical data store. Re-running initialization after a partial failure must not create duplicates or corrupt parent/child relationships.

**Pattern**
Initialize the unit's data space as a logical partition keyed by the unit, not as a separate physical store. Initialization is idempotent: it detects what already exists, remaps parent/child references deterministically, and only inserts what is missing. Master data is distributed from a controlling center through an idempotent "distribute if missing" operation.

**Rules**
- Initialization can be re-run safely at any point; repeated runs converge to the same state.
- A control-level setting defines what the unit may create itself versus what only the center can issue; attempts beyond that level are rejected, not silently accepted.
- Distribution never overwrites unit-local modifications unless an explicit supersede action is invoked.
- All initialization steps are ordered so that referenced data exists before referencing data.

**Acceptance**
Prove initialization, repeated initialization (convergence), parent/child remapping, control-level rejection of unauthorized local creation, and refusal of operations on a unit that was never initialized — with read-back from the data store matching the reported state.

## 3. Composite Uniqueness When a Partition Dimension Is Added | 新增分区维度时的复合唯一性

**Problem**
A single-column uniqueness constraint that was correct before partitioning blocks legitimate records: two units now need records carrying the same natural code, and cross-unit operations fail with uniqueness conflicts.

**Pattern**
Rebuild the affected uniqueness constraint as a composite constraint that includes the partition dimension, so the natural code is unique *within a unit*, not globally.

**Rules**
- Every uniqueness constraint is reviewed whenever a new partition dimension is introduced; leaving a stale single-column constraint is a known defect, not a tolerable warning.
- Historical rows are migrated to a valid value under the new constraint before the constraint is enforced.
- The composite constraint uses the same ordering and matching semantics as the rest of the schema (no case- or collation-dependent surprises).

**Acceptance**
Demonstrate same-code records coexisting across units, a true duplicate still being rejected within one unit, and a migration that completes with no orphaned rows violating the rebuilt constraint.

## 4. Cross-Unit Collaboration State Machine | 跨单元协同状态机

**Problem**
An action in one unit must produce corresponding, potentially split records in one or more counterpart units. Both sides need to see differences, correct them, and cancel safely, while preventing the originating record from being reversed while the collaboration is outstanding.

**Pattern**
Drive collaboration from explicit templates that define the counterpart structure — one-to-one, or one-to-many with proportional allocation (rounding remainder assigned to a defined last recipient). Initiating a collaboration generates counterpart *drafts*; recipients review, save with difference marking, request re-initiation, or cancel. A small state machine governs the lifecycle, and occupied collaborations block reverse operations on the source record.

**Rules**
- Allocation rules are deterministic; rounding remainders are handled by a stated rule, never left unallocated.
- Counterpart drafts are written through a dedicated, allow-listed write path restricted to draft state; the general write path and its guards remain unchanged.
- While a collaboration is active, the source record cannot be unapproved or deleted; the block is enforced on the write path, not only in the interface.
- Re-initiation and cancellation skip already-deleted rows and remain idempotent.
- Soft deletion must be proven to persist; a soft-delete call that does not reach the store is a defect.

**Acceptance**
Over multiple rounds, prove template types, proportional allocation with remainder handling, difference marking, re-initiation, cancellation, the block on source reversal, and soft-delete persistence — with store read-back and on-screen state agreeing, and totals equal to the sum of line items.

## 5. Read-Only Aggregation Across Independent Data Spaces | 跨独立数据空间只读汇总

**Problem**
Decision-makers need a consolidated view across units that keep independent data spaces, but cross-space access is dangerous, and naive consolidation can double-count or silently apply inappropriate elimination.

**Pattern**
Maintain three explicit configurations: the consolidation group, its member spaces, and a mapping of local codes to a canonical vocabulary. Access each space through a double allow-list (pattern validation plus a registered space list). Read only confirmed/approved data. Present each member in parallel columns plus a total column, under a declared consolidation rule.

**Rules**
- Cross-space references use fully qualified names validated against both a pattern and a registry; unregistered spaces are unreachable.
- The consolidation rule is stated explicitly — e.g., "sum only, no elimination" — and the implementation never does more than the rule says.
- Unmapped codes follow a defined fallback (direct collection by code), not a silent drop.
- Every aggregated figure supports drill-down: aggregate → member source → underlying record, with amounts traceable end to end.

**Acceptance**
Prove the double allow-list rejection of an unregistered space, parallel columns plus a total that equals the member sum, the no-elimination rule, unmapped-code fallback, and full drill-down to an underlying record with matching amounts.

## 6. Rule-Driven Collection with Idempotent Settlement | 规则驱动汇集与幂等结算

**Problem**
Periodic settlement must gather records from multiple sources under configurable rules, and re-running the process after a failure must not generate duplicate settlement records.

**Pattern**
Enabled rules define which sources are collected and how they are grouped. Each generated settlement line carries a composite key of source type, source identifier, and unit key, so re-collection finds the existing line instead of inserting a new one. The operation is reversible through an explicit reverse action that preserves the audit chain.

**Rules**
- Intermediate calculations use a defined high precision; persistence uses the standard precision, with a stated rounding rule.
- Bidirectional flows (e.g., movement between two units) populate both directions under a pairing identifier.
- Reverse operations never hard-delete; they mark reversal and retain the full history.
- The first check of every operation is the feature switch; when the capability is off, it refuses rather than returning empty success.

**Acceptance**
Prove collection from all configured sources, idempotent re-runs (zero new lines), correct rounding at the precision boundary, reversal with retained audit history, and refusal when the capability is disabled.

# Part II — Configuration, Reuse and Gateway Patterns | 配置化、复用与网关模式

## 7. One Template + Declarative Configs + Registry | 一模板 + 声明式配置 + 注册表

**Problem**
Many screens differ only in field selection and data source, yet teams build and maintain one bespoke page per view, multiplying code and defects.

**Pattern**
Build one generic template driven by declarative configurations, and register every entry in a single registry that maps a route key to a configuration. Adding a view becomes adding a configuration, not a page.

**Rules**
- Configurations are data: field sets, data source keys, and capability gates — never embedded logic.
- Configured views pass through the same capability gating (feature switches, allowed flows) as bespoke pages; configuration is not a way to bypass a gate.
- The registry is the only entry mechanism; unregistered routes are unreachable.

**Acceptance**
Prove multiple distinct views rendered from one template with different configurations, gate enforcement on a configured view, and refusal of an unregistered route.

---

## 8. Cross-Cutting Engines Write Back Through the Command Gateway | 横切引擎经命令网关回写

**Problem**
A cross-cutting engine (workflow, approval, scheduling) needs to update business records, but letting it write directly creates an uncontrolled second write path and allows direct actions that bypass the engine.

**Pattern**
The engine never writes business data itself. Its results are handed to the command gateway, which performs the write under a system identity with the same validation and guards as any other command. Bypass prevention is two-layer: the presentation layer hides direct action entries when the engine is bound, and the write layer rejects direct commands from non-system sources.

**Rules**
- Every engine-driven write carries an identifiable system origin; the write layer rejects the same action from any other origin.
- Variables needed by the engine (approvers, mappings) are resolved and validated fail-fast before the process starts.
- The engine's outcome (approve/cancel) is a separate bridge object; the business record is only changed through gateway commands.

**Acceptance**
Prove an engine-bound record cannot be directly approved or unapproved from either the interface or a direct command, the engine result writes correctly through the gateway under system identity, and invalid engine configuration fails before execution rather than mid-process.

---

## 9. Capability Allow-List with Least Privilege | 能力白名单最小授权

**Problem**
A powerful tool (especially one that can generate artifacts or reach external systems) must be made available to some roles without opening a broad authorization band.

**Pattern**
Grant the tool per role through an explicit allow-list under least privilege: only the roles that need it, only the risk band required (e.g., read-only artifact generation, explicit write-back prohibition). Synchronize the grant in three places: the platform template, a cursor-based backfill over existing tenants, and automatic provisioning for new tenants.

**Rules**
- The grant is minimal and additive; roles that do not need the tool are unchanged.
- Risk bands are explicit (draft/read-only, no write-back); widening a band is a separate, reviewed change.
- Asynchronous triggers return immediately with a rebuilt context snapshot; the long operation runs detached and emits an artifact-level event on completion.
- Links to generated artifacts pass through authenticated retrieval; a bare link that fails authorization is a defect.

**Acceptance**
Prove an allowed role can invoke the tool, a non-allowed role is rejected, the write-back prohibition holds, existing and newly provisioned tenants carry the same grant, and the artifact link retrieves successfully under authentication.

# Part III — Automation and Governance Patterns | 自动化与治理模式

## 10. Race-Condition Governance in Automated Walkthroughs | 自动化走查竞态治理

**Problem**
Automated navigation between views in a single-page application produces false failures: after triggering navigation, the tool only checks "content exists", and residual content from the previous view is mistaken for readiness. Asynchronous route guards may also raise blocking prompts during the transition.

**Pattern**
After navigation, wait for the **target identity** (target URL/route in effect), not merely for any content. Actively detect and dismiss guard blocking prompts, raise the polling budget for slow environments, and fall back to a full-page load of the target if the route does not settle.

**Rules**
- Readiness requires both target identity and a stable content selector; old-page residue never counts as ready.
- Blocking prompts are dismissed programmatically; repeated prompts with no target transition trigger the full-page fallback.
- The fix lives in the test tooling, not the product; product behavior is not changed to satisfy a flawed check.
- A "tooling false positive" must be distinguished from a real product defect by re-running the exact failing view in isolation.

**Acceptance**
Re-run the full walkthrough suite: every previously false-positive page passes, the target identity is asserted on every navigation, and genuine product defects still fail (the tool has not been weakened to always pass).

## 11. Two-Layer Engineering Telemetry | 两层工程遥测

**Problem**
Six categories of engineering data are needed for governance and research — usage economics, escape rate, human-versus-AI source distinction, true/false-positive labels on gate blocks, bypass and coverage time series, and rework detail — but instrumentation must not create a second system or ever block delivery.

**Pattern**
Two layers. The collection layer writes local append-only event logs: idempotent, database-independent, with a global switch and a uniform envelope, and it never blocks the main flow. The ingestion layer, only when a connection is available, idempotently loads events into the store using idempotency keys; a single failed record never aborts the batch.

**Rules**
- Collection is append-only with an idempotency key; replayed events are skipped, not duplicated.
- Every telemetry call fails safe: hook and CI wrappers always succeed regardless of telemetry outcome.
- Unresolvable entities fall back to a default mapping so events are never lost.
- The schema is provisioned idempotently across all tenants; repeated provisioning keeps the table count constant.

**Acceptance**
Prove first-run insertion then replay-skip for all six event categories, correct tenant distribution, non-blocking behavior when the store is unreachable, idempotent schema provisioning with constant table counts, and unchanged exit semantics of the underlying git/CI operations.

## 12. Failure Observability: Name the Object and Evidence Domain | 失败可观测性：点名对象与证据域

**Problem**
When a gate fails, the error only names the step, while the continuous system discards the detailed artifact. The exact failing record and evidence domain cannot be located from logs, so diagnosis restarts from scratch.

**Pattern**
Make failure messages diagnostic without changing pass/fail logic: each blocked object reports its identity and the evidence domains that did not pass, and the final error lists every failed object across every failed scope.

**Rules**
- Diagnostic enhancement never alters a judgment; the same passing run still passes.
- Each failure carries object identity, state, failed evidence domains, and reason.
- Multi-step failures are concatenated with delimiters so no failed step is hidden.

**Acceptance**
Run a deliberately failing gate and confirm the output identifies the exact object and evidence domain; run a passing gate and confirm unchanged success.

## 13. Freshness Governance for Derived Artifacts | 派生产物新鲜度治理

**Problem**
Generated handbooks and derived views can silently remain at an old version after their sources change, so readers act on stale information while the build looks healthy.

**Pattern**
Bind every derived artifact to a source hash and generation timestamp, and enforce a freshness gate: after a source change, an un-rebuilt artifact fails.

**Rules**
- The hash of the true source is recorded at generation time; staleness is computed by comparing current source hash to the recorded one.
- The freshness gate fails closed: missing hash or missing artifact is a failure, not a warning.
- Derived artifacts are regenerated through the maintained generator; manual edits to derived outputs are prohibited.

**Acceptance**
Change a source without rebuilding and confirm the gate fails; rebuild through the generator and confirm it passes; confirm a missing artifact is treated as a failure.

---

## 14. Cache-Miss Must Fall Back to Source | 缓存未命中必须回源

**Problem**
A runtime registry returns an empty result when its cache is empty, and the empty cache is mistaken for "no data exists", silently hiding published records.

**Pattern**
On any cache miss — including an empty cache — fall back to the authoritative source (the registry or persistent store), then populate the cache. "Empty" is only reported after the source confirms it.

**Rules**
- Cache state is never treated as authoritative on a miss.
- The fallback path is tested with an empty cache, not just an expired entry.
- A source failure surfaces as an error, never as an empty success.

**Acceptance**
With an empty cache, prove the fallback retrieves the records and fills the cache; with a genuinely empty source, prove the empty result is returned only after source confirmation; with a source failure, prove an error surfaces.

# Part IV — Environment and Interaction Patterns | 环境与交互模式

## 15. Link-Aware Cleanup and Occupancy Recognition | 链接感知清理与占用识别

**Problem**
Recursive cleanup can traverse junction points, links, or mount points into the main workspace and delete shared data; on some systems, directories held by running processes also cause cleanup to fail midway.

**Pattern**
Before any deletion, identify links and junction points and resolve them first (unlink rather than recurse), and detect processes occupying the target. Only after links are detached and occupancy is resolved do you remove plain files.

**Rules**
- Bare recursive deletion is prohibited wherever a link may exist; link detection is the first step.
- Every resolved path is confirmed to stay inside the intended target before deletion.
- Occupied paths are reported with the occupant; the operation does not repeatedly retry a locked path.
- Disposable material and genuine work-in-progress are distinguished; only disposable material is purged.

**Acceptance**
On a tree containing a junction, prove the junction is detached without touching the link target; on an occupied path, prove the occupant is reported; on a normal tree, prove cleanup succeeds and work-in-progress is retained.

---

## 16. Inline-Priority Layout for High-Frequency Selectors | 高频选择器内联优先

**Problem**
"Inline-first" budget rules can collapse a frequently used entity selector into a "more" overflow, hiding a primary filter and forcing extra clicks on a core workflow.

**Pattern**
Classify selectors by usage frequency: high-frequency selectors are inline by default and cannot be folded into overflow; the collapse budget applies only to low-frequency fields.

**Rules**
- Frequency classification is explicit per field; it is not decided by generic space pressure alone.
- Walkthroughs cover the collapsed path too, so a field hidden in overflow is still verified.
- A selector that was inline must not regress into overflow during an unrelated refactor.

**Acceptance**
Prove the high-frequency selector renders inline on the relevant pages, low-frequency fields still collapse, and the overflow path is covered by the automated walkthrough.
