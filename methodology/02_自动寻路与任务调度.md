# 02 — Auto-Pathfinding & Task Scheduling | 自动寻路与任务调度

> **Part of**: Enterprise-Grade Full AI Development Methodology
> **Prerequisites**: 00_核心方法论白皮书, 01_Skill体系分层架构
> **Stack scope**: universal. Routing logic is technology-neutral; concrete tech skills are selected only after the stack is verified.

---

## 1. The Auto-Pathfinding Problem | 自动寻路问题

When a developer makes a natural-language request such as "add an approval workflow to this business process", the AI must answer:

1. **Which project line?** -> determine the task line
2. **Which rules apply?** -> AGENTS.md, project rules, data rules
3. **Which skill leads?** -> depends: backend-first if a new contract is needed, frontend-first if it is a UI change
4. **What to check first?** -> the existing data structure, existing flow, current permission setup
5. **Execution order?** -> data change -> model -> service -> interface -> frontend -> integration test

**This is the auto-pathfinding problem**: given a natural language request, determine the optimal execution path through the skill system.

---

## 2. The Routing Algorithm | 路由算法

The ai-rule-dispatcher implements a deterministic routing algorithm:

`
INPUT: User request (natural language)

STEP 1: Classify Task Line
  - Contains "fix"/"bug"? -> mainline
  - Contains "audit"/"check"/"review"? -> audit
  - Contains "competitor"/"research"/"market"? -> research
  - Contains "deploy"/"release"? -> release
  - Contains "architecture"/"boundary"/"domain"? -> governance
  - Default: mainline

STEP 2: Classify Task Type
  - Cross-module (frontend + backend + data)? -> ai-task-decomposer
  - Architecture decision needed? -> ai-architect-governor
  - Project scheduling? -> ai-chief-planner
  - Command execution? -> ai-command-executor
  - Otherwise: direct to execution layer

STEP 3: Match the Verified Stack
  - Select the tech skill that matches the stack already verified from project evidence
    (frontend skill for UI work, backend skill for service work, data skill for schema work,
    container skill for container work). Do not assume a stack from a single keyword.

STEP 4: Select First Documents
  - Always: rules/AGENTS.md
  - If project rules exist: load them
  - Lead skill's SKILL.md
  - Relevant docs/ category

STEP 5: Define Pre-Checks
  - Data changes -> inspect current structures
  - Code changes -> file existence, pattern search
  - Runtime -> port check, health endpoint

OUTPUT: Routing result with lead skill, support skills, docs, checks
`

## 3. Task Line Priority System | 任务线优先级

Multiple task lines can be active simultaneously:

| Line | Priority | Typical Owner | Max Parallel |
|---|---|---|---|
| **Mainline** | Highest | Primary developer | Active development |
| **Governance** | High | Architect | Architecture decisions |
| **Audit** | Medium | Reviewer | Quality checks |
| **Research** | Low | Anyone | Investigation |
| **Release** | Highest (during release window) | DevOps | Deployment |

### Line Conflict Resolution

When tasks from multiple lines compete for the same resource:
1. **Release line** takes absolute priority during release windows
2. **Mainline blocker fixes** take priority over new feature work
3. **Governance decisions** that block mainline get expedited
4. **Research** is always preemptible

## 4. Dependency-Aware Scheduling | 依赖感知调度

The ai-task-decomposer produces a dependency graph:

`mermaid
graph TD
    A[B-01: Data change] --> B[B-02: Model layer]
    A --> C[B-03: Test data]
    B --> D[B-04: Service layer]
    D --> E[B-05: Interface layer]
    E --> F[B-06: Frontend service]
    F --> G[B-07: Frontend page]
    C --> H[B-08: Integration test]
    E --> H
    G --> H
`

### Scheduling Rules

| Rule | Description |
|---|---|
| **Blocker-first** | Tasks that unblock others execute first |
| **No hot-file collision** | Tasks writing to the same file cannot run in parallel |
| **Frontend waits for the contract** | Frontend work starts only after endpoints are testable |
| **Tests wait for implementation** | Integration tests start after both frontend and backend complete |

## 5. Routing Examples | 路由示例

### Example 1: "Fix the search that returns an error"

`
Classification:
  Line: mainline (bug fix)
  Type: execution (specific file/contract)
  Stack: depends on the verified project tech

Routing:
  Lead: the backend skill (if backend) or frontend skill (if frontend)
  First check: server logs, health endpoint, error stack trace
  Docs: rules/AGENTS.md
  Pre-check: reproduce the failing call, check error log
`

### Example 2: "Add a new analytical report"

`
Classification:
  Line: mainline (feature)
  Type: decomposition (new report = data + backend + frontend)
  Stack: the project's verified backend and frontend skills

Routing:
  Lead: ai-task-decomposer (break into batches)
  First docs: rules/AGENTS.md, existing report examples
  Pre-checks: relevant data structures, existing report patterns, permission setup

Decomposition output:
  B-01: Data — add report query structures
  B-02: Backend — report service + interface
  B-03: Frontend — report page + filters
  B-04: Integration test
`

### Example 3: "Audit a set of flows for closure"

`
Classification:
  Line: audit
  Type: governance (quality audit)

Routing:
  Lead: ai-flow-closure-audit
  Support: ai-domain-boundary-mapper
  First docs: rules/AGENTS.md, existing process docs
  Pre-checks: the relevant module code, endpoints, data schema

Output: closure audit report with prioritized gaps
`

## 6. When Auto-Pathfinding Fails | 自动寻路失败时

The dispatcher has an **escalation path**:

1. **Ambiguous request** -> Ask the user one clarifying question (not multiple)
2. **Unknown domain** -> Route to ai-chief-planner for research-based scheduling
3. **Conflict detected** -> Flag the conflict, defer to human decision
4. **No matching skill** -> Route to ai-skill-evolver to create a skill candidate
