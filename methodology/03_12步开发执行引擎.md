# 03 — 13-Step Development Execution Engine | 13步开发执行引擎

> **Part of**: Enterprise-Grade Full AI Development Methodology
> **Prerequisites**: 00_核心方法论白皮书, 01_Skill体系分层架构
> **Stack scope**: universal. The layer names and gates below are technology-neutral; map each step to the equivalent construct in the project's own stack (see §6).

---

## 1. Why a Fixed Order? | 为什么需要固定顺序？

In traditional development, the order of operations is implicit. In AI-assisted development, **explicit ordering prevents three classes of errors**:

| Error Class | Example | Prevention |
|---|---|---|
| **Frontend-first trap** | Building a UI before the contract exists | Enforced: frontend starts at Step 7 |
| **Skip-verification trap** | Writing code without checking data state | Enforced: every step has mandatory verification |
| **Assumption drift** | assuming a data structure exists that was never created | Enforced: Step 1 is always data verification |

## 2. The 13 Steps | 完整13步

### Backend Phase | 后端阶段

#### Step 1: Data Store Initialization & Verification
`
Actions:
  1. Check current schema/structure (list tables/collections, inspect target)
  2. Write a migration/change script (if structures are new or modified)
  3. Execute the script
  4. Verify: structures exist, columns/fields match, row counts as expected

Artifacts: versioned migration script under the project's migrations folder
Gate: All structures/fields exist and match specification
`

#### Step 2: Entity / Model Layer
`
Actions:
  1. Generate model types from the data schema
  2. Document every field
  3. Add validation rules/constraints
  4. Verify: field names match the data columns/fields exactly

Artifacts: model source file (or equivalent)
Gate: Every data field has a corresponding model property with documentation
`

#### Step 3: Repository / Data-Access Layer
`
Actions:
  1. Create a data-access component following the project's base repository pattern
  2. Add custom query operations with the project's query mechanism
  3. Verify: execute each custom query, check result correctness

Artifacts: repository component and its query definitions
Gate: All custom queries return expected results
`

#### Step 4: Service / Business-Logic Layer
`
Actions:
  1. Implement business logic in the service component
  2. Declare transaction boundaries
  3. Add cache configuration if needed
  4. Verify: write and run unit tests

Artifacts: service component + tests
Gate: All unit tests pass
`

#### Step 5: Interface / API Layer
`
Actions:
  1. Expose standard create/read/update/delete endpoints through the project's interface style
  2. Add interface documentation
  3. Apply authorization rules
  4. Verify: invoke each endpoint, check response format

Artifacts: interface/controller component
Gate: All endpoints return correct status and data format
`

#### Step 6: Build & Startup Verification
`
Actions:
  1. Clean build/compile using the project's build tool (or equivalent)
  2. Start the service locally
  3. Check the health/readiness endpoint
  4. Smoke test: one call per new endpoint

Artifacts: Build log, health check response
Gate: Build succeeds, service starts, health is UP
`

### Frontend Phase | 前端阶段

#### Step 7: Contract / Type Generation
`
Actions:
  1. Generate client-side contract types from the backend models/DTOs
  2. Verify: every field matches the backend, types are correct
  3. Document the types

Artifacts: client type definitions (or equivalent)
Gate: Contract fields 1:1 match the backend DTO
`

#### Step 8: Frontend Service / API-Client Layer
`
Actions:
  1. Create an API client with typed methods
  2. Add error handling (network errors, business errors)
  3. Add request/response interceptors if needed
  4. Verify: call each method, inspect the network activity

Artifacts: client service component
Gate: All API calls succeed with correct response types
`

#### Step 9: Component / Page
`
Actions:
  1. Build the page using the project's component framework and conventions
  2. Follow existing component patterns
  3. Implement loading, empty, error states
  4. Verify: open the page in a browser, test all interactions

Artifacts: page/component source (or equivalent)
Gate: Page renders correctly, all CRUD operations work
`

### Integration Phase | 联调阶段

#### Step 10: Integration Testing
`
Actions:
  1. End-to-end workflow test (create -> read -> update -> delete)
  2. Edge case testing (invalid input, concurrent operations)
  3. Error handling test (backend down, network error)
  4. Verify: all test cases pass

Artifacts: Test report
Gate: All integration test cases pass
`

#### Step 11: Seed Data & Validation
`
Actions:
  1. Write test data scripts
  2. Load them into the test data store
  3. Verify data in the UI (every field renders correctly)
  4. Edge cases: null values, max-length strings, special characters

Artifacts: seed/test data script
Gate: All seed data displays correctly in UI
`

#### Step 12: Schema Sync & Release
`
Actions:
  1. Compare the template schema with all instance schemas
  2. Generate sync scripts for any drift
  3. Execute sync
  4. Verify: all schemas match the template

Artifacts: schema sync script
Gate: Zero schema drift across all instances
`

#### Step 13: Browser Runtime Verification
`
Actions:
  1. Verify the backend is running on the target port
  2. Run the runtime-verify capability of the ai-runtime-verify skill against the app URL
  3. Check output: "passed" must be true
  4. If P0 checks fail -> fix errors and re-run Step 13
  5. If P1 warnings -> note and decide whether to fix before release

Artifacts: project-owned verification output and/or captured screenshots
Gate: All P0 checks must pass:
  - No console errors
  - Loading overlay removed properly
  - Core DOM elements render with content
  - All API calls return 2xx/3xx
  - No white screen / blank page
  - No infinite refresh loop

CRITICAL RULE:
  An AI agent MUST NOT declare "development complete"
  unless runtime verification returns "passed": true.
`

## 3. Verification Checklist | 验证清单

Every step has a **binary gate**: pass or block. No "mostly done."

`
[ ] Step 1:  Data structures exist and match spec     ─── BLOCK if fail
[ ] Step 2:  Model fields match data fields           ─── BLOCK if fail
[ ] Step 3:  Custom queries return expected results   ─── BLOCK if fail
[ ] Step 4:  Unit tests pass                          ─── BLOCK if fail
[ ] Step 5:  Endpoints return correct responses       ─── BLOCK if fail
[ ] Step 6:  Build succeeds, service healthy          ─── BLOCK if fail
[ ] Step 7:  Contract types match backend DTOs        ─── BLOCK if fail
[ ] Step 8:  API client calls succeed                 ─── BLOCK if fail
[ ] Step 9:  Page renders, CRUD works                 ─── BLOCK if fail
[ ] Step 10: Integration tests pass                   ─── BLOCK if fail
[ ] Step 11: Seed data displays correctly             ─── BLOCK if fail
[ ] Step 12: All schemas synced                       ─── BLOCK if fail
[ ] Step 13: Runtime verify passes                    ─── BLOCK if fail
`

## 4. Exceptions & Shortcuts | 例外与捷径

Shortcuts are **explicitly allowed** in these cases:

| Scenario | Allowed Shortcut |
|---|---|
| Pure UI fix (no API/data change) | Skip Steps 1-6, start at Step 7. Step 13 always required. |
| Pure data migration | Only Steps 1 + 12 |
| Documentation only | Skip all steps, go directly to docs |
| Configuration change | Steps 1 (verify) + 6 (build) + 12 (sync) |

**Rule**: Any shortcut must be explicitly stated with justification before execution begins.

---

## 5. Common Violations & Consequences | 常见违规与后果

| Violation | Consequence |
|---|---|
| Skipping data check (Step 1) | Code written against wrong schema -> errors |
| Writing frontend before the backend contract (Step 7 before 5) | UI built against an imaginary contract -> rework |
| Skipping build verification (Step 6) | Build errors discovered late -> cascading fixes |
| No integration test (Step 10) | Regressions discovered in production |
| Schema sync skipped (Step 12) | Multi-instance drift -> production failures |
| Runtime verify skipped (Step 13) | Page loads with errors, broken UX -> false "done" claim |

## 6. Stack Mapping (illustrative, not prescriptive) | 技术栈映射（示例，非指定）

The skeleton is fixed; the concrete constructs are chosen by the project's verified stack. These are examples of how a neutral step maps onto different families — no family is mandatory:

| Neutral step | Compiled OO stack example | Dynamic/interpreted stack example |
|---|---|---|
| Step 2 model | class with validation annotations | typed interface / schema object |
| Step 3 repository | base repository + query definitions | data-access module / query builder |
| Step 4 transaction | declarative transaction annotation | transaction/session helper |
| Step 6 build | dependency-tool build + readiness endpoint | interpreter startup + readiness route |
| Step 7 contract | generated client types | generated schema/client |
| Step 9 component | component framework page | server-rendered or client component |

Select the matching tech skill only after the stack has been verified from real project evidence; never assume a stack from a single file extension.
