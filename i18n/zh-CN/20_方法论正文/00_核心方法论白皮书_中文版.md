## 概述 | Executive Summary

本方法论定义了一套**完整、可自我进化的 AI 辅助企业级软件开发系统**，覆盖完整生命周期：

```text
Requirements  ->  Plan  ->  Task Decomposition  ->  Auto-Pathfinding
     ->  Code Execution  ->  Test Writing  ->  MD Documentation Writeback
     ->  Skill Auto-Evolution
```

与“氛围编程（vibe coding）”——开发者松散地提示 AI、指望碰巧得到好结果——不同，本方法论把**工程纪律引入 AI 辅助开发**：强制先检查后执行、13 步开发顺序、数据驱动的真相源，以及每完成一项任务就变强一次的自我进化 Skill 体系。

### 为什么需要这套方法论 | Why This Exists

AI 编码工具市场正在爆发——Cursor、Codex、Copilot、Windsurf——但这个市场有一个巨大的空洞：

| 已有的 | 缺失的 |
|---|---|
| AI 编码工具 | 在企业级规模上使用它们的**系统性方法论** |
| 单文件 .cursorrules | 带路由、分解、进化的**多层 Skill 架构** |
| 氛围编程（松散提示） | 面向 AI 生成代码的**工程纪律** |
| 临时性使用 AI | **可复现、可审计**的 AI 开发过程 |

本方法论填补这个空洞。它不是凭空设计出来的——它是在构建一套真实多租户 ERP 系统（采购、销售、库存、财务、生产、CRM、WMS、TMS）的烈火中锻造出来的，横跨 42+ 个专用 AI Skill 与 2000+ 份文档产物。

## 1. 核心引擎 | The Core Engine

本方法论由一套**五层 Skill 架构（L0–L4）**驱动：

### 第 0 层：分类层 | Layer 0: Classification
**Skill**：ai-project-classifier

在路由任何任务之前，先按来源（origin）、质量目标（quality target）、部署目标（deploy targets）与规模（scale）对项目分类。不确定时默认按 AI 原生（AI-Native）处理；若选择了更轻量的模式，必须记录该降级决策。

### 第 1 层：路由层 | Layer 1: Routing
**Skill**：ai-rule-dispatcher

在任何任务开始之前，本层回答：
- 本任务属于哪条项目线？
- 必须先读哪些规则与文档？
- 应由哪个 Skill 主导执行？
- 必须先完成哪些事实核查（数据库、代码、运行时）？

### 第 2 层：分解层 | Layer 2: Decomposition
**Skill**：ai-task-decomposer

复杂任务被分解为安全、可执行的批次：
- 范围冻结（Scope freeze，明确范围内 / 范围外）
- 现状核验 与 目标设计 与 实现 三者的分离
- 依赖感知排序
- 每个批次的验收标准与证据规则

### 第 3 层：执行层 | Layer 3: Execution
**Skills**：领域专用 Skill（backend-dev、frontend-dev、database-manager 等）

执行层遵循**强制 13 步开发顺序**：

| # | 后端 | 前端 |
|---|---|---|
| 1 | 数据库初始化与验证 | — |
| 2 | 实体层 | — |
| 3 | Mapper/Repository 层 | — |
| 4 | 服务层（业务逻辑） | — |
| 5 | 控制器（Controller）/API 层 | — |
| 6 | 构建与编译验证 | — |
| 7 | — | TypeScript 接口生成 |
| 8 | — | 服务（Service）/API 层 |
| 9 | — | Vue/React 组件开发 |
| 10 | 集成测试 | 集成测试 |
| 11 | 种子数据与验证 | UI 冒烟测试 |
| 12 | Schema 同步与发布 | 构建与部署 |

每一步都**必须经过验证**才能进入下一步，禁止跳步。

### 第 4 层：进化层 | Layer 4: Evolution
**Skill**：ai-skill-evolver

每当任务完成，进化层负责：
1. 识别重复出现的模式、错误或上下文缺失
2. 对缺口分类（更新 Skill、新建 Skill、更新文档、修改规则）
3. 更新对应的 SKILL.md 或新建一个
4. 把进化记录写入 Skill 归档
5. 把变更同步到当前启用的 AI 工具（Codex、Cursor 等）

### Qualification 与成熟度 | Qualification and maturity

存在不等于交付。一个路由、菜单、注册表条目或可见按钮，只能证明某项能力存在。必须记录由 fresh evidence（新鲜证据）支撑的最高 qualification（交付资格）：

| Qualification | 含义 |
|---|---|
| Q0 | 能力已存在于源码、注册表或路由中 |
| Q1 | 参数、权限、状态、配置与依赖已对齐 |
| Q2 | 后端编排、提供方覆盖、唯一副作用路径与审计收口完成 |
| Q3 | 真实业务验收、对账、跨客户端/运行时（cross-client/runtime）证据与发布证据全部收口 |

使用统一的共享能力成熟度链：

```text
registered -> configured -> authorized -> provider-covered
            -> runtime-executable -> business-closed
```

即：已注册 → 已配置 → 已授权 → 提供方已覆盖 → 运行时可执行 → 业务已闭环。

HTTP 200、健康检查、页面可见、CI 通过或一次本地提交，任何单独一项都不能证明达到 Q3 或业务闭环。

## 2. 工程纪律 | Engineering Discipline

以下是区分本方法论与氛围编程的**非协商规则**：

### 2.1 先检查后执行 | Check Before Execute
**绝不假设，必须核实。**
- 改数据库（DB）前：SHOW TABLES; DESCRIBE table; SELECT COUNT(*)
- 改代码前：核实文件是否存在，grep 现有模式
- 改运行时前：检查端口、进程、日志

### 2.2 禁止降级方案 | No Degradation
**定位根因，彻底修复。**
- 禁止临时绕过
- 禁止“先让它跑起来”的补丁
- 每处修复都必须解决底层问题

### 2.3 数据驱动开发 | Data-Driven Development
**数据库（DB）是唯一真相源。**
- 所有结构性决策都从数据库核验开始
- 代码与文档跟随数据库，而不是反过来
- Schema 变更必须走正式迁移脚本

### 2.4 零废话界面 | Zero-Fluff UI
**ERP / SaaS / admin 管理后台页面不含任何装饰性文案。**
- 禁止欢迎语、营销文案与占位式帮助文本
- 只保留可操作提示：字段约束、校验规则、业务风险警示
- 使用工具提示与行内校验，禁止独立说明段落

### 2.5 计划驱动 | Plan-Driven Execution
**任何任务在执行前都必须有计划。**
- 任务分析、复杂度评估、Skill 匹配
- 逐步计划，每一步都带验收标准
- PDCA 循环：Plan -> Do -> Check -> Act

## 3. 文档体系 | Documentation System

本方法论包含一套**自我生长的文档体系**，分为六类：

| 类别 | 用途 | 更新频率 |
|---|---|---|
| **架构决策记录（ADR）** | 跨领域架构决策 | 每次决策 |
| **每日调研回写** | 自动化每日状态报告 | 每日 |
| **业务流程文档** | 端到端业务流程文档 | 每次流程变更 |
| **部署与运维** | 部署指南、回滚步骤 | 每次发布 |
| **测试与验收** | 测试计划、回归记录 | 每个测试轮次 |
| **项目总控** | 整体项目状态、任务看板 | 持续 |

文档体系**不是为写文档而写文档**——它是**记忆层**，让 AI 智能体跨会话保持上下文，并让新的智能体即刻上手。

## 4. Skill 自动进化 | Skill Auto-Evolution

这是本方法论最独特的能力。与静态规则文件不同，Skill 体系**越用越强**：

```text
Task Execution -> Pattern Detection -> Gap Classification
     -> Skill Update/Creation -> Archive Record -> Next Task Benefits
```

### 进化触发条件 | Evolution Triggers
- 跨模块重复出现的任务模式
- 重复出现的错误或上下文缺失时刻
- 应当被固化的稳定产出模板
- 项目路径或规则变更
- 用户反馈某个 Skill 不生效

### 进化动作 | Evolution Actions
- 用新模式更新既有 SKILL.md
- 当一个模式跨越 2+ 种任务类型时，新建 Skill
- 更新 Skill 成熟度评级（declared -> callable -> effective -> evolving）
- 在 Skill 归档中记录进化证据

## 6. 快速开始 | Getting Started

### 新项目初始化 | For a New Project

```bash
# 1. Copy the rules engine
cp rules/AGENTS.md {your-project}/

# 2. Copy core methodology skills
cp -r skills/core/ {your-project}/skills/
cp -r skills/governance/ {your-project}/skills/

# 3. Select relevant tech stack skills
cp -r skills/tech/{your-stack}/ {your-project}/skills/

# 4. Initialize documentation structure
cp -r docs/_templates/ {your-project}/docs/

# 5. Run first-project audit
# Use ai-rule-dispatcher to analyze your project and generate initial recommendations
```

### 已有项目迁移 | For an Existing Project

1. 运行 ai-rule-dispatcher 做项目审计
2. AI 将分析现有代码库、数据库与文档
3. 产出差距分析报告
4. 增量引入方法论各层（不要试图一口气煮沸整个海洋）
