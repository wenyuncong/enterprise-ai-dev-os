## 1 为什么需要部署门禁？| Why Deployment Gates?

AI 生成的代码与人手写的代码走同一条部署流水线。没有显式门禁时，AI 可能把以下东西部署出去：

- 能编译但在运行时出错的代码
- 能通过测试但在生产环境崩溃的代码
- 在本地可用、在远端服务器失败的 SQL 迁移
- 使用了错误环境变量的配置

**门禁体系把 AI 生成的代码与人手写的代码完全同等对待——没有例外。**

## 2 部署前门禁 | Pre-Deployment Gates

### 门禁 1（Gate 1）：构建验证 | Build Verification

```bash
# Must pass with zero errors
mvn clean compile -DskipTests    # or equivalent
npm run build                    # frontend
```

### 门禁 2（Gate 2）：单元测试门禁 | Unit Test Gate

```bash
# All tests must pass
mvn test                         # backend
npm run test                     # frontend
```

### 门禁 3（Gate 3）：数据库 Schema 门禁（模板 —— 使用项目自有检查）| Database Schema Gate (Template — use project-owned checks)

```bash
# Zero schema drift between template and all instances
{project-schema-sync-command}

# Required tables and columns exist in all schemas
{project-database-baseline-command}
```

本方法论不附带通用的数据库迁移脚本，因为正确的命令取决于项目所用的数据库、迁移工具、租户模型和部署环境。把选定的项目自有命令记录在交付契约（DeliveryContract）或部署运维手册中。

### 门禁 4（Gate 4）：代码质量门禁 | Code Quality Gate

```bash
# Linting passes
npm run lint                     # frontend
# Static analysis passes
mvn verify                       # backend
```

### 门禁 5（Gate 5）：安全扫描 | Security Scan

```bash
# No known vulnerabilities in dependencies
npm audit --production           # frontend
mvn dependency-check:check       # backend
```

## 4 验收标准 | Acceptance Criteria

### 单功能验收 | Per-Feature Acceptance

| 验收项 | 所需证据 |
|---|---|
| **功能完整性** | 全部验收测试用例通过 |
| **错误处理** | 非法输入返回正确的错误码 |
| **边界情况** | 空值、空串、最大长度、特殊字符均已测试 |
| **性能** | 响应时间在 SLA 之内（例如 CRUD 小于 500ms） |
| **安全** | 接口要求认证，且校验授权 |
| **文档** | API 文档已更新，架构变更则补 ADR |

### 单次发布验收 | Per-Release Acceptance

| 验收项 | 门禁 |
|---|---|
| **全部部署前门禁为绿** | 构建、测试、Schema、静态检查、安全 |
| **预发布环境冒烟测试通过** | 健康检查、登录、核心 CRUD |
| **P0/P1 缺陷未关闭数为零** | 已核对缺陷跟踪系统 |
| **回滚方案已成文** | 已撰写并已实测 |
| **发布说明已发布** | 变更日志 + 迁移指南 |

## 5 回滚流程 | Rollback Procedure

每次部署都必须有一条**经过实测的回滚路径**：

```bash
# 1. Stop current deployment
systemctl stop app-service

# 2. Restore previous artifact
cp /backups/app-v{previous}.jar /deploy/app.jar

# 3. Rollback DB migrations (if reversible)
flyway undo

# 4. Start previous version
systemctl start app-service

# 5. Verify health
curl http://localhost:8080/actuator/health
```

**规则**：如果回滚耗时超过 5 分钟，说明这次部署没有被正确门禁。

## 6 监控与告警 | Monitoring & Alerts

部署之后，监控以下指标：

| 指标 | 告警阈值 | 动作 |
|---|---|---|
| 错误率 | 超过请求量的 1% | 立即排查 |
| 响应时间 | 超过基线的 2 倍 | 检查是否出现回归 |
| 内存占用 | 超过上限的 80% | 可能存在内存泄漏 |
| 数据库连接数 | 超过连接池的 80% | 检查连接泄漏 |
| 健康检查端点 | 非 UP | 重启服务 |

## 7 AI 特有部署规则 | AI-Specific Deployment Rules

| 规则 | 原因 |
|---|---|
| **AI 禁止直接部署到生产环境** | 生产部署必须有人工评审 |
| **AI 生成的 SQL 必须经过评审** | DDL 失误可能导致数据丢失 |
| **AI 在声称「完成」之前必须跑完部署前门禁** | 防止「在我机器上能编译」 |
| **AI 必须为每次迁移产出回滚脚本** | 未经明确批准，不得引入不可逆变更 |
