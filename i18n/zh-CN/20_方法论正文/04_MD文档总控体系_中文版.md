## 1 为什么 AI 开发需要文档 | Why Documentation Matters in AI Development

智能体（AI agent）有一个根本性限制：**跨会话没有持久记忆**。每个新会话启动时，对之前发生过什么都处于零上下文状态。

没有文档体系时：

- AI 重复同样的调研
- AI 犯同样的错误
- AI 无法引用过去的决策
- 每个会话都在「从零开始」

MD 文档体系是桥接 AI 会话的**记忆层**。

## 2 六类文档体系 | The Six-Category System

```text
docs/
  _templates/                    ← Templates for new projects
  |
  架构决策记录/                   ← Category 1: Architecture Decision Records
  每日调研回写/                   ← Category 2: Daily Investigation Writebacks
  业务流程全案/                   ← Category 3: Business Process Documentation
  部署运维手册/                   ← Category 4: Deployment & Operations
  测试验收报告/                   ← Category 5: Testing & Acceptance
  全项目总控/                     ← Category 6: Master Project Control Hub
```

### 类别 1：架构决策记录（ADR）| Category 1: Architecture Decision Records (ADR)

**用途**：记录架构决策**为什么**这样做。

**模板**：ADR 格式，含背景、决策、备选方案、后果。

**更新频率**：每产生一个决策。

**示例条目**：

```text
ADR-001: Multi-Tenant Schema Isolation
Status: Accepted
Decision: Each tenant gets a separate database schema
Alternatives: Shared tables with tenant_id column (rejected: security risk)
Consequences: Schema sync complexity, but full data isolation
```

### 类别 2：每日调研回写 | Category 2: Daily Investigation Writebacks

**用途**：自动记录每日发现、决策和 Skill 进化触发条件。

**更新频率**：每个开发会话。

**示例条目**：

```text
2026-06-17 — Purchase Order Save Performance
Finding: purchase_order table missing index on tenant_id + order_date
Action: Added composite index, query time dropped from 2.3s to 0.1s
Skill affected: mysql-best-practices — add index optimization pattern
```

### 类别 3：业务流程全案 | Category 3: Business Process Documentation

**用途**：记录端到端业务流程，并验证所有分层。

**更新频率**：每次流程变更。

**内容**：流程图、逐步细节、相关实体、参数、回写路径。

### 类别 4：部署运维手册 | Category 4: Deployment & Operations

**用途**：部署指南、回滚步骤、环境配置。

**更新频率**：每次发布。

**内容**：服务器搭建、构建命令、环境变量、健康检查、回滚步骤。

### 类别 5：测试验收报告 | Category 5: Testing & Acceptance

**用途**：测试计划、测试用例、回归记录、验收签署。

**更新频率**：每个测试轮次。

**内容**：测试用例矩阵、通过/失败（pass/fail）结果、缺陷跟踪、验收结论。

### 类别 6：全项目总控 | Category 6: Master Project Control Hub

**用途**：项目总体状态、任务看板、里程碑跟踪、Skill 成熟度矩阵。

**更新频率**：持续更新。

**内容**：主任务看板、里程碑进展、Skill 清单、团队分工。

## 3 文档回写循环 | The Writeback Loop

文档不是一个独立阶段——它嵌在执行循环里：

```text
Task Execution
    |
    v
Writeback Decision: Does this task produce a reusable finding?
    |
    +-- YES --> Write to the relevant doc category
    |            |
    |            v
    |           ai-skill-evolver triggered (if pattern detected)
    |
    +-- NO  --> No writeback needed (trivial task)
```

### 什么需要回写 | What Gets Written Back

| 发现 | 类别 |
|---|---|
| 架构决策 | 架构决策记录 |
| 调研结果 | 每日调研回写 |
| 业务流程变更 | 业务流程全案 |
| 部署配置变更 | 部署运维手册 |
| 测试结果 | 测试验收报告 |
| 项目状态变更 | 全项目总控 |

### 什么不回写 | What Does NOT Get Written Back

- 琐碎的缺陷修复（错别字、颜色改动）
- 单行代码改动
- 例行依赖升级
- 已经记录过的发现

## 4 文档即 AI 记忆 | Documentation as AI Memory

新 AI 会话启动时，按以下顺序读取文档：

```text
1. rules/AGENTS.md             ← Core rules
2. docs/全项目总控/             ← Current project state
3. docs/每日调研回写/ (last 3)  ← Recent context
4. docs/架构决策记录/            ← Architecture decisions
5. Task-specific docs           ← Relevant to current task
```

这相当于让 AI 在 30 秒内完成「读完团队过去一周的 Slack 记录」。

---

## 5 AI 文档金科玉律 | The "Golden Rule" of AI Documentation

> **「为下一个 AI 会话写文档，而不是为后人写文档。」**

传统文档是写给几个月后的人看的。AI 文档是写给**几个小时后启动的下一个 AI 会话**的。这意味着：

- **精炼，不冗长** —— AI 读得快，但上下文窗口有限
- **结构化，不叙事** —— 用表格和清单，不用大段散文
- **可验证，不臆测** —— 引用文件路径、行号、数据库（DB）表
- **可执行，不描述** —— 每条记录都应当驱动一个决策或动作

## 6 反模式 | Anti-Patterns

| 反模式 | 为什么失败 |
|---|---|
| **什么都写文档** | 污染上下文，AI 无法在噪声中找到信号 |
| **只为人类写文档** | 散文式文档浪费 AI 上下文窗口 |
| **没有每日回写** | 每个 AI 会话都从零开始 |
| **文档散落在随机位置** | AI 无法发现相关上下文 |
| **文档过期** | AI 相信文档甚于代码，做出错误决策 |
