## 1 为什么需要标准结构？| Why a Standard Structure?

对 GERP 项目的分析揭示：

| 问题 | 根本原因 | 修复方式 |
|---|---|---|
| 项目根目录散落 55 个文件 | 缺少根目录纪律 | 根目录只保留 AGENTS.md + .editorconfig |
| `database/` 下约 300 个散落 SQL 文件 | 没有子文件夹约定 | 按用途建立子文件夹 |
| `docs/` 混乱：任务包、领域文档、发布文档混放 | 没有文档层级 | 按类型建立子文件夹树 |
| 中英文文件夹名混用 | 没有命名规范 | 代码强制 ASCII，文档强制 UTF-8 |

**原则**：文件夹结构必须匹配项目的架构原型（archetype）与规模。快速原型不应当与企业级系统使用同一套结构。

## 2 根目录标准 | Root-Level Standard

### 根目录（项目根目录）放什么 | What goes in root (project root)

```
{project}/
  AGENTS.md              ← 必需：方法论章程
  .editorconfig          ← 必需：编码/换行符规则
  .gitignore             ← 必需
  README.md              ← 项目概览（不是方法论文档）
  package.json           ← 若为 Node.js 项目
  pom.xml / build.gradle ← 若为 Java 项目（或放在 backend/ 下）
```

### 绝对禁止放进根目录的内容 | What NEVER goes in root

- 脚本 → `scripts/`
- SQL → `database/`
- 文档 → `docs/`
- 临时文件 → `temp/` 或 `tmp/`
- 配置 → `config/` 或 `backend/config/`
- 日志 → `logs/`

## 4 数据库文件夹标准 | Database Folder Standard

**GERP 的问题**：`database/` 下有约 300 个散落 SQL 文件，什么都找不到。

**解决方案**：按用途建立子文件夹。

```
database/
  migrations/            ← V{NNN}__description.sql（Flyway 格式）
    V001__init_schema.sql
    V002__add_user_table.sql
  seed/                  ← 种子/测试数据，一个模块一个文件
    seed_users.sql
    seed_products.sql
  schema/                ← 参考文档（自动生成，不手写）
    schema_v1.0.md
  backup/                ← 备份脚本
    backup_full.sql
  tools/                 ← 模式比对、同步工具
    sync_schema.py
```

**命名规则**：

- 迁移文件：`V{NNN}__{description}.sql`（Flyway 标准）
- 种子文件：`seed_{module}.sql`
- `database/` 根目录禁止散落 SQL 文件——**审计自动判失败（auto-fail audit）**

## 5 文档子文件夹层级 | Docs Sub-Folder Hierarchy

**某个遗留 ERP 的问题**：文档根目录把带日期的任务包文件夹与领域文件夹混在一起，无法区分任务包、领域文档和发布文档。

**解决方案**：先按类型，再按主题。

```
docs/
  _templates/            ← 模板（禁止直接编辑）
    架构决策记录/
    每日调研回写/
    业务流程全案/
    测试验收报告/
    部署运维手册/
    全项目总控/

  架构决策记录/           ← 每个决策一份文件
    ADR-001_多租户架构选型.md
    ADR-002_原子服务拆分策略.md

  每日调研回写/           ← 每天一份文件
    2026-06-17_可行性分析.md
    2026-06-18_技术选型.md

  业务流程全案/           ← 每个流程一个子文件夹
    采购流程/
      00_总览.md
      01_采购订单.md
      02_采购入库.md
    销售流程/
      00_总览.md

  测试验收报告/           ← 每轮测试一份文件
    2026-06_R1_核心流程测试.md
    2026-06_R2_回归测试.md

  部署运维手册/           ← 每个环境一份文件
    dev_部署指南.md
    prod_部署指南.md
    回滚流程.md

  全项目总控/             ← 总控
    MASTER_INDEX.md       ← 自动生成的 Skill/模式/文档索引
    PROJECT_STATUS.md     ← 当前阶段、进行中任务、阻塞项
```

**规则**：

- 任务包放进其所属领域文件夹，禁止写成散落的 `docs/{name}_任务包_{date}/`
- 发布文档放进 `docs/发布闭环/`（如需要）或 `docs/部署运维手册/`
- `docs/` 根目录禁止散落 `.md` 文件

## 6 命名规范 | Naming Convention

| 类型 | 规范 | 示例 |
|---|---|---|
| 文件夹（代码） | kebab-case，仅 ASCII | `auth-service/`、`user-profile/` |
| 文件夹（文档） | 中文或 kebab-case（同一项目内保持一致） | `架构决策记录/` 或 `adr/` |
| 文件（代码） | 类用 PascalCase，其余用 camelCase | `UserService.java`、`formatDate.ts` |
| 文件（文档） | `{date}_{topic}.md` 或 `{prefix}-{NNN}_{topic}.md` | `2026-06-17_部署.md`、`ADR-001_架构.md` |
| SQL 迁移 | `V{NNN}__{description}.sql` | `V001__init_schema.sql` |

**执行方式**：`ai-component-standardizer` 在项目初始化时审计文件夹命名。

## 7 GERP 做得好的 | What GERP Got Right

| 模式 | 为什么有效 |
|---|---|
| `backend/gerp-modules/` 下按领域分子文件夹 | 模块边界清晰，可独立构建 |
| `frontend/` 下按平台分子项目 | Web、移动端、小程序彼此独立 |
| `scripts/` 下按类型分子文件夹 | `bat/`、`ps1/`、`py/`——按工具类型查找 |
| `docker/` 下按环境分子文件夹 | `dev/`、`prod/`、`test-server/`——用途清晰 |
| 原始 Skill 归档单独保留 | 保留经实战检验的源材料，同时只把清理后的 `skills/` 作为正式 Skill 根目录对外暴露 |

## 8 GERP 的问题 | What GERP Got Wrong (and We Fixed)

| 问题 | 我们的修复 |
|---|---|
| 根目录散落 55 个文件 | 只保留 AGENTS.md + .editorconfig + 构建文件 |
| `database/` 下约 300 个散落 SQL | 建立 `migrations/`、`seed/`、`schema/`、`backup/` 子文件夹 |
| `docs/` 扁平无层级 | 类型 → 领域 → 日期结构 |
| 中英文文件夹混用 | 按项目保持一致的规则 |
| 多个 AI 工具配置（6 个工具） | 以 `skills/` 为标准化源，再用 `tools/deploy.ps1` 部署到各工具适配器文件夹 |
