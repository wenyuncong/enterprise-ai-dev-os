## 1 为什么需要固定顺序？ | Why a Fixed Order?

在传统开发中，操作顺序是隐含的。在 AI 辅助开发中，**显式排序可防止三类错误**：

| 错误类别 | 示例 | 预防措施 |
|---|---|---|
| **前端先行陷阱** | 契约尚不存在就先建界面 | 强制：前端从 Step 7 开始 |
| **跳过验证陷阱** | 不核对数据状态就写代码 | 强制：每一步都有强制验证 |
| **假设漂移** | 假设某个从未创建的数据结构已存在 | 强制：Step 1 始终是数据验证 |

## 2 完整13步 | The 13 Steps

### 后端阶段 | Backend Phase

#### 步骤 1：数据存储初始化与验证 | Step 1: Data Store Initialization & Verification

```
操作：
  1. 检查当前 schema/结构（列出表/集合，检查目标）
  2. 编写迁移/变更脚本（新建或变更结构时）
  3. 执行脚本
  4. 验证：结构存在、列/字段匹配、行数符合预期

产物：项目 migrations 目录下的版本化迁移脚本
门禁：所有结构/字段存在且与规格一致
```

#### 步骤 2：实体 / 模型层 | Step 2: Entity / Model Layer

```
操作：
  1. 由数据 schema 生成模型类型
  2. 为每个字段编写文档
  3. 添加校验规则/约束
  4. 验证：字段名与数据列/字段完全一致

产物：模型源文件（或等价物）
门禁：每个数据字段都有对应的模型属性且带文档
```

#### 步骤 3：仓储 / 数据访问层 | Step 3: Repository / Data-Access Layer

```
操作：
  1. 按项目基础仓储模式创建数据访问组件
  2. 用项目的查询机制添加自定义查询操作
  3. 验证：逐条执行自定义查询，检查结果正确性

产物：仓储组件及其查询定义
门禁：所有自定义查询返回预期结果
```

#### 步骤 4：服务 / 业务逻辑层 | Step 4: Service / Business-Logic Layer

```
操作：
  1. 在服务组件中实现业务逻辑
  2. 声明事务边界
  3. 按需添加缓存配置
  4. 验证：编写并运行单元测试

产物：服务组件 + 测试
门禁：所有单元测试通过
```

#### 步骤 5：接口 / API 层 | Step 5: Interface / API Layer

```
操作：
  1. 按项目接口风格暴露标准增删改查端点
  2. 添加接口文档
  3. 应用授权规则
  4. 验证：调用每个端点，检查响应格式

产物：接口/控制器组件
门禁：所有端点返回正确状态码与数据格式
```

#### 步骤 6：构建与启动验证 | Step 6: Build & Startup Verification

```
操作：
  1. 用项目构建工具做干净构建/编译（或等价命令）
  2. 本地启动服务
  3. 检查健康/就绪端点
  4. 冒烟测试：每个新增端点各调一次

产物：构建日志、健康检查响应
门禁：构建成功、服务启动、健康状态为 UP
```

### 前端阶段 | Frontend Phase

#### 步骤 7：契约 / 类型生成 | Step 7: Contract / Type Generation

```
操作：
  1. 由后端模型/DTO 生成客户端契约类型
  2. 验证：每个字段与后端一致，类型正确
  3. 为类型编写文档

产物：客户端类型定义（或等价物）
门禁：契约字段与后端 DTO 1:1 对应
```

#### 步骤 8：前端服务 / API 客户端层 | Step 8: Frontend Service / API-Client Layer

```
操作：
  1. 创建带类型方法的 API 客户端
  2. 添加错误处理（网络错误、业务错误）
  3. 按需添加请求/响应拦截器
  4. 验证：逐个调用方法，检查网络活动

产物：客户端服务组件
门禁：所有 API 调用成功且响应类型正确
```

#### 步骤 9：组件 / 页面 | Step 9: Component / Page

```
操作：
  1. 用项目组件框架与规范构建页面
  2. 遵循现有组件模式
  3. 实现加载、空、错误状态
  4. 验证：在浏览器打开页面，测试所有交互

产物：页面/组件源（或等价物）
门禁：页面正确渲染，所有增删改查操作可用
```

### 联调阶段 | Integration Phase

#### 步骤 10：集成测试 | Step 10: Integration Testing

```
操作：
  1. 端到端流程测试（创建 -> 读取 -> 更新 -> 删除）
  2. 边界用例测试（非法输入、并发操作）
  3. 错误处理测试（后端宕机、网络错误）
  4. 验证：所有测试用例通过

产物：测试报告
门禁：所有集成测试用例通过
```

#### 步骤 11：种子数据与验证 | Step 11: Seed Data & Validation

```
操作：
  1. 编写测试数据脚本
  2. 装入测试数据存储
  3. 在界面中验证数据（每个字段都正确渲染）
  4. 边界用例：空值、最大长度字符串、特殊字符

产物：种子/测试数据脚本
门禁：所有种子数据在界面中正确显示
```

#### 步骤 12：Schema 同步与发布 | Step 12: Schema Sync & Release

```
操作：
  1. 比对模板 schema 与所有实例 schema
  2. 针对任何漂移生成同步脚本
  3. 执行同步
  4. 验证：所有 schema 与模板一致

产物：schema 同步脚本
门禁：所有实例零 schema 漂移
```

#### 步骤 13：浏览器运行时验证 | Step 13: Browser Runtime Verification

```
操作：
  1. 确认后端已在目标端口运行
  2. 运行 ai-runtime-verify 技能的运行时验证能力，指向应用 URL
  3. 检查输出："passed" 必须为 true
  4. 若 P0 检查失败 -> 修复错误并重跑 Step 13
  5. 若为 P1 警告 -> 记录，并决定是否在发布前修复

产物：项目自有验证输出及/或截图
门禁：P0 检查必须全部通过：
  - 无控制台错误
  - 加载遮罩被正确移除
  - 核心 DOM 元素渲染出内容
  - 所有 API 调用返回 2xx/3xx
  - 无白屏 / 空白页
  - 无无限刷新循环

关键规则：
  AI 智能体禁止宣称“开发完成”，
  除非运行时验证返回 "passed": true。
```

## 3 验证清单 | Verification Checklist

每一步都有**二元门禁**：通过或阻断。没有“基本完成”。

```
[ ] Step 1:  数据结构存在且与规格一致        ─── 失败即阻断
[ ] Step 2:  模型字段与数据字段一致          ─── 失败即阻断
[ ] Step 3:  自定义查询返回预期结果          ─── 失败即阻断
[ ] Step 4:  单元测试通过                    ─── 失败即阻断
[ ] Step 5:  端点返回正确响应                ─── 失败即阻断
[ ] Step 6:  构建成功，服务健康              ─── 失败即阻断
[ ] Step 7:  契约类型与后端 DTO 一致         ─── 失败即阻断
[ ] Step 8:  API 客户端调用成功              ─── 失败即阻断
[ ] Step 9:  页面渲染，增删改查可用          ─── 失败即阻断
[ ] Step 10: 集成测试通过                    ─── 失败即阻断
[ ] Step 11: 种子数据正确显示                ─── 失败即阻断
[ ] Step 12: 所有 schema 已同步              ─── 失败即阻断
[ ] Step 13: 运行时验证通过                  ─── 失败即阻断
```

## 4 例外与捷径 | Exceptions & Shortcuts

捷径在以下情形**被明确允许**：

| 场景 | 允许的捷径 |
|---|---|
| 纯界面修复（无 API/数据变更） | 跳过 Step 1–6，从 Step 7 开始。Step 13 始终必需。 |
| 纯数据迁移 | 仅 Step 1 + Step 12 |
| 仅文档 | 跳过所有步骤，直接进文档 |
| 配置变更 | Step 1（验证）+ Step 6（构建）+ Step 12（同步） |

**规则**：任何捷径都必须在执行开始前明确说明并给出理由。

## 5 常见违规与后果 | Common Violations & Consequences

| 违规 | 后果 |
|---|---|
| 跳过数据检查（Step 1） | 针对错误 schema 写代码 -> 错误 |
| 后端契约未就绪就写前端（在 Step 5 之前做 Step 7） | 针对想象中的契约建界面 -> 返工 |
| 跳过构建验证（Step 6） | 构建错误发现过晚 -> 连锁修复 |
| 无集成测试（Step 10） | 回归在生产环境暴露 |
| 跳过 schema 同步（Step 12） | 多实例漂移 -> 生产故障 |
| 跳过运行时验证（Step 13） | 页面带着错误加载、交互损坏 -> 虚假“已完成”宣称 |

## 6 技术栈映射（示例，非指定） | Stack Mapping (illustrative, not prescriptive)

骨架固定，具体构件由项目已验证的技术栈决定。下表展示中立步骤如何映射到不同技术族，任何族都不是强制的：

| 中立步骤 | 编译型面向对象栈示例 | 动态/解释型栈示例 |
|---|---|---|
| Step 2 模型 | 带校验注解的类 | 类型化接口 / schema 对象 |
| Step 3 仓储 | 基础仓储 + 查询定义 | 数据访问模块 / 查询构造器 |
| Step 4 事务 | 声明式事务注解 | 事务/会话辅助 |
| Step 6 构建 | 依赖工具构建 + 就绪端点 | 解释器启动 + 就绪路由 |
| Step 7 契约 | 生成的客户端类型 | 生成的 schema/客户端 |
| Step 9 组件 | 组件框架页面 | 服务端渲染或客户端组件 |

只有在从真实项目证据验证技术栈之后，才选择匹配的技术技能；不要仅凭单个文件扩展名假设技术栈。
