## 1 为什么需要固定顺序？ | Why a Fixed Order?

在传统开发中，操作顺序是隐含的。在 AI 辅助开发中，**显式排序可防止三类错误**：

| 错误类别 | 示例 | 预防措施 |
|---|---|---|
| **前端先行陷阱** | API 尚不存在就先建 UI | 强制：前端从 Step 7 开始 |
| **跳过验证陷阱** | 不核对 DB 状态就写代码 | 强制：每一步都有强制验证 |
| **假设漂移** | AI 假设某张从未创建的表已存在 | 强制：Step 1 始终是 DB 验证 |

## 2 完整13步 | The 13 Steps

### 后端阶段 | Backend Phase

#### 步骤 1：数据库初始化与验证 | Step 1: Database Initialization & Verification

```
操作：
  1. 检查：SHOW TABLES; DESCRIBE target_table;
  2. 编写 SQL 迁移脚本（新建或变更表时）
  3. 执行脚本
  4. 验证：SHOW TABLES; DESCRIBE target_table; SELECT COUNT(*);

产物：database/migrations/V{NNN}__description.sql
门禁：所有表/列存在且与规格一致
```

#### 步骤 2：实体 / 模型层 | Step 2: Entity / Model Layer

```
操作：
  1. 由 DB schema 生成实体类
  2. 为每个字段加注释
  3. 添加校验注解
  4. 验证：字段名与 DB 列名完全一致

产物：{module}/entity/{Entity}.java（或等价物）
门禁：每个 DB 列都有对应的实体字段且带注释
```

#### 步骤 3：Mapper / Repository 层 | Step 3: Mapper / Repository Layer

```
操作：
  1. 创建 mapper 接口，继承 BaseMapper/Repository
  2. 添加自定义查询方法，配 XML/注解 SQL
  3. 验证：逐条执行自定义查询，检查结果正确性

产物：{module}/mapper/{Entity}Mapper.java + XML
门禁：所有自定义查询返回预期结果
```

#### 步骤 4：Service 层 | Step 4: Service Layer

```
操作：
  1. 在 service 类中实现业务逻辑
  2. 添加事务管理（@Transactional）
  3. 按需添加缓存配置
  4. 验证：编写并运行单元测试

产物：{module}/service/{Entity}Service.java + 测试
门禁：所有单元测试通过
```

#### 步骤 5：Controller / API 层 | Step 5: Controller / API Layer

```
操作：
  1. 创建 REST controller，提供标准 CRUD 端点
  2. 添加 API 文档（Swagger/OpenAPI 注解）
  3. 添加权限注解
  4. 验证：curl 每个端点，检查响应格式

产物：{module}/controller/{Entity}Controller.java
门禁：所有端点返回正确的 HTTP 状态码与数据格式
```

#### 步骤 6：构建与编译验证 | Step 6: Build & Compile Verification

```
操作：
  1. 干净编译：mvn clean compile（或等价命令）
  2. 本地启动服务
  3. 检查健康端点：/actuator/health
  4. 冒烟测试：每个新增端点各调一次 API

产物：构建日志、健康检查响应
门禁：构建成功、服务启动、健康状态为 UP
```

### 前端阶段 | Frontend Phase

#### 步骤 7：TypeScript 接口生成 | Step 7: TypeScript Interface Generation

```
操作：
  1. 由后端 DTO/Entity 生成 TypeScript 接口
  2. 验证：每个字段与后端一致，类型正确
  3. 添加 JSDoc 注释

产物：{app}/src/types/{Entity}.ts
门禁：接口字段与后端 DTO 1:1 对应
```

#### 步骤 8：前端 Service / API 层 | Step 8: Frontend Service / API Layer

```
操作：
  1. 创建带类型方法的 API service
  2. 添加错误处理（网络错误、业务错误）
  3. 按需添加请求/响应拦截器
  4. 验证：逐个调用方法，检查 Network 面板

产物：{app}/src/services/{Entity}Service.ts
门禁：所有 API 调用成功且响应类型正确
```

#### 步骤 9：前端组件 / 页面 | Step 9: Frontend Component / Page

```
操作：
  1. 创建 Vue/React 组件
  2. 遵循项目组件规范
  3. 实现加载、空、错误状态
  4. 验证：在浏览器打开页面，测试所有交互

产物：{app}/src/views/{Entity}/index.vue（或等价物）
门禁：页面正确渲染，所有 CRUD 操作可用
```

### 联调阶段 | Integration Phase

#### 步骤 10：集成测试 | Step 10: Integration Testing

```
操作：
  1. 端到端流程测试（创建 → 读取 → 更新 → 删除）
  2. 边界用例测试（非法输入、并发操作）
  3. 错误处理测试（后端宕机、网络错误）
  4. 验证：所有测试用例通过

产物：测试报告
门禁：所有集成测试用例通过
```

#### 步骤 11：种子数据与验证 | Step 11: Seed Data & Validation

```
操作：
  1. 编写测试数据脚本
  2. 插入测试数据库
  3. 在 UI 中验证数据（每个字段都正确渲染）
  4. 边界用例：空值、最大长度字符串、特殊字符

产物：database/seed/{module}_test_data.sql
门禁：所有种子数据在 UI 中正确显示
```

#### 步骤 12：Schema 同步与发布 | Step 12: Schema Sync & Release

```
操作：
  1. 比对模板 schema 与所有实例 schema
  2. 针对任何漂移生成同步脚本
  3. 执行同步
  4. 验证：所有 schema 与模板一致

产物：database/sync/{date}_schema_sync.sql
门禁：所有实例零 schema 漂移
```

## 3 验证清单 | Verification Checklist

每一步都有**二元门禁**：通过或阻断。没有“基本完成”。

```
[ ] Step 1:  DB 表存在且与规格一致            ─── 失败即阻断
[ ] Step 2:  实体字段与 DB 列一致             ─── 失败即阻断
[ ] Step 3:  自定义查询返回预期结果           ─── 失败即阻断
[ ] Step 4:  单元测试通过                     ─── 失败即阻断
[ ] Step 5:  API 端点返回正确响应             ─── 失败即阻断
[ ] Step 6:  构建成功，服务健康               ─── 失败即阻断
[ ] Step 7:  TS 接口与后端 DTO 一致           ─── 失败即阻断
[ ] Step 8:  API service 调用成功             ─── 失败即阻断
[ ] Step 9:  页面渲染，CRUD 可用              ─── 失败即阻断
[ ] Step 10: 集成测试通过                     ─── 失败即阻断
[ ] Step 11: 种子数据正确显示                 ─── 失败即阻断
[ ] Step 12: 所有 schema 已同步               ─── 失败即阻断
[ ] Step 13: 运行时验证通过                   ─── 失败即阻断
```

---

#### 步骤 13：浏览器运行时验证 | Step 13: Browser Runtime Verification

```
操作：
  1. 确认后端服务已在目标端口运行
  2. 运行：node skills/governance/ai-runtime-verify/scripts/verify.js --url {APP_URL}
  3. 检查输出："passed" 必须为 true
  4. 若 P0 检查失败 → 修复错误并重跑 Step 13
  5. 若为 P1 警告 → 记录，并决定是否在发布前修复

产物：项目自有验证输出，或
skills/governance/ai-runtime-verify/screenshots/verify-{timestamp}.png
门禁：6 项 P0 检查必须全部通过：
  - 无控制台错误
  - 加载遮罩被正确移除
  - 核心 DOM 元素渲染出内容
  - 所有 API 调用返回 2xx/3xx
  - 无白屏 / 空白页
  - 无无限刷新循环

⚠️ 关键规则：
  AI 智能体禁止宣称“开发完成”，
  除非 ai-runtime-verify 返回 "passed": true。
```

## 4 例外与捷径 | Exceptions & Shortcuts

捷径在以下情形**被明确允许**：

| 场景 | 允许的捷径 |
|---|---|
| 纯 UI 修复（无 API/DB 变更） | 跳过 Step 1–6，从 Step 7 开始。Step 13 始终必需。 |
| 纯 DB 迁移 | 仅 Step 1 + Step 12 |
| 仅文档 | 跳过所有步骤，直接进文档 |
| 配置变更 | Step 1（验证）+ Step 6（编译）+ Step 12（同步） |

**规则**：任何捷径都必须在执行开始前明确说明并给出理由。

---

## 5 常见违规与后果 | Common Violations & Consequences

| 违规 | 后果 |
|---|---|
| 跳过 DB 检查（Step 1） | 针对错误 schema 写代码 → 500 错误 |
| 后端 API 未就绪就写前端（在 Step 5 之前做 Step 7） | 针对想象中的 API 建 UI → 返工 |
| 跳过构建验证（Step 6） | 编译错误发现过晚 → 连锁修复 |
| 无集成测试（Step 10） | 回归在生产环境暴露 |
| 跳过 schema 同步（Step 12） | 多租户漂移 → 生产故障 |
| 跳过运行时验证（Step 13） | 页面带着 JS 错误加载、交互损坏 → AI 宣称已完成但页面不可用 |
