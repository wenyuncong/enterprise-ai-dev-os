## 1. 为什么老项目不能当新项目做？| Why Brownfield ≠ Greenfield

新项目（greenfield）假设你面对的是一张白纸。老项目（brownfield）则是在活体上做手术。差别如下：

| | 新项目（Greenfield） | 老项目（Brownfield） |
|---|---|---|
| **起点** | 空目录 | 带历史的既有代码库 |
| **架构** | 可以从零设计 | 必须在既有架构内工作 |
| **风险容忍度** | 高（没有什么可弄坏的） | 低（用户/数据都依赖它） |
| **模式来源** | 方法论提供模式 | 项目提供模式（提炼，不强加） |
| **Skill 进化** | Skill 从新模式中生长 | Skill 从**提炼出的**模式中生长 |
| **速度** | 快（没有约束） | 可变（取决于代码质量） |

**老项目改造的黄金法则**：**既有项目是老师，你的方法论是学生。** 先提炼模式，再决定保留什么、修复什么、替换什么。

## 2. 干预深度分级 | Intervention Spectrum

并非所有老项目工作都需要深度改造。先定级。

```
┌─────────────────────────────────────────────────────────────┐
│                   干预深度分级（INTERVENTION SPECTRUM）       │
├────────┬────────┬──────────┬──────────┬────────────────────┤
│ 1 级   │ 2 级   │ 3 级     │ 4 级     │ 5 级               │
│ 快速   │ 功能   │ 模块     │ 深度     │ 接管               │
│ 修复   │ 追加   │ 升级     │ 改造     │ （半成品）         │
├────────┼────────┼──────────┼──────────┼────────────────────┤
│1-2 小时│1-5 天  │1-4 周    │1-6 个月  │ 持续进行           │
│缺陷修复│新增功能│重构      │重构架构  │ 继承 + 收尾        │
└────────┴────────┴──────────┴──────────┴────────────────────┘
```

### Level 1：快速修复（Quick Fix）（1-2 小时）
**适用**：缺陷修复、少量文案改动、简单功能追加
**做法**：
- 读受影响文件 + 它的直接依赖
- 完全匹配既有代码风格
- 禁止重构任何无关内容
- 只测试改动到的那条路径
**门禁**：修复生效，且没有弄坏别的东西

### Level 2：功能追加（Feature Addition）（1-5 天）
**适用**：在既有架构内新增一个模块/功能
**做法**：
- 研究 2-3 个同类既有模块，提炼模式
- 完全照抄它们的结构、命名、模式
- 不做架构变更
**门禁**：新功能可用，且与既有模式一致

### Level 3：模块升级（Module Upgrade）（1-4 周）
**适用**：重构单个模块，同时保持接口稳定
**做法**：
- 对该模块做深度审计（代码、DB、API、测试）
- 改任何东西之前先提炼模式
- 重构内部实现，保持公开 API 稳定
- 用提炼出的模式更新 Skill
**门禁**：模块质量提升，依赖它的模块无回归

### Level 4：深度改造（Deep Renovation）（1-6 个月）
**适用**：重构架构、迁移技术栈、多模块重构
**做法**：
- 全项目审计（所有模块、所有层）
- 模式提炼 → 创建/更新 Skill
- 每项改动配架构决策记录
- 增量推进：一次一个模块，保持系统可运行
**门禁**：每个模块独立通过，系统始终可用

### Level 5：接管（Takeover）（持续进行）
**适用**：继承另一个团队/开发者留下的半成品工作
**做法**：
- 全面审计：什么能用、什么不能用、缺什么
- 如实记录当前状态（而不是记录「本应」是什么样）
- 对工作项分类：可用 / 有缺陷 / 未完成 / 完全缺失
- 按依赖关系而非愿望清单排定「收尾顺序」
**门禁**：真实状态已记录，可落地的收尾计划已建立

## 3. 六阶段改造流程 | The 6-Phase Brownfield Workflow

```
阶段 1：AUDIT    → 现有什么？当前状态如何？
阶段 2：CLASSIFY → 属于哪个干预级别？质量目标是什么？
阶段 3：EXTRACT  → 保留哪些模式？修复哪些？→ 反哺 Skill
阶段 4：PLAN     → 做什么、按什么顺序、承担什么风险？
阶段 5：EXECUTE  → 外科手术式修改，尊重既有模式
阶段 6：EVOLVE   → 把提炼出的模式回写到 Skill
```

#### 1.2 代码质量扫描 | Code Quality Scan
```markdown
## 代码质量发现（Code Quality Findings）
| 问题 | 严重级 | 受影响文件 | 建议 |
|---|---|---|---|
| 没有测试 | P0 | 全部模块 | 优先为关键路径补测试 |
| 命名规范混用 | P1 | 约 40% 文件 | 逐步统一 |
| 多服务间逻辑重复 | P1 | 认证、校验 | 抽到共享模块 |
| 硬编码配置值 | P1 | 约 15 个文件 | 移入 config/env |
| 缺少错误处理 | P2 | 若干端点 | 补 try/catch 与错误响应 |
```

```markdown

| 风险 | 可能性 | 影响 | 缓解措施 |
|---|---|---|---|
| 弄坏既有功能 | 高 | 高 | 重构前先补齐回归测试 |
| 数据库迁移失败 | 中 | 致命 | 先备份、空跑迁移、准备回滚方案 |
| 性能退化 | 低 | 中 | 前后各自做基准测试 |
```

### 阶段 2：CLASSIFY — 干预分级 | Determine Intervention Level

依据审计发现 + 用户目标判定：

| 问题 | 决定什么 |
|---|---|
| 用户真正想要的是什么？ | 是修一处，还是整体改造 |
| 有多紧急？ | 本次干预的时间盒 |
| 代码质量基线如何？ | 现实可达的范围 |
| 有用户正在依赖它吗？ | 风险容忍度 |
| 这是半成品工作吗？ | 接管还是改造 |

**产出**：Level 1-5 分级，并给出明确的范围边界。

### 阶段 3：EXTRACT — 模式提炼 | Pattern Mining

**Skill 正是从这里从存量代码中进化的。** 每个项目都有模式——有好有坏。两者都要提炼。

#### 3.1 值得保留并固化的好模式 | Good Patterns to Keep and Formalize
```markdown
## 提炼出的模式 → Skill 更新（Extracted Patterns → Skill Updates）

### 模式：[Name]
- **出现位置**： [文件/模块]
- **它做什么**： [描述]
- **为什么有效**： [分析]
- **要更新的 Skill**： [Skill 名]
- **更新内容**： [要向该 Skill 补充什么]
```

#### 3.2 需要修复的坏模式（反模式）| Bad Patterns to Fix (Anti-Patterns)
```markdown
## 发现的反模式 → 修复计划（Anti-Patterns Found → Fix Plan）

### 反模式：[Name]
- **出现位置**： [受影响文件]
- **问题是什么**： [问题描述]
- **影响**： [会导致什么——缺陷、性能问题、维护痛苦]
- **修复做法**： [如何重构]
- **优先级**： [P0/P1/P2]
```

#### 3.3 提炼产出的去向 | Extraction Output Feeds
```
提炼出的模式     → ai-skill-evolver         → 更新/创建 Skill
提炼出的反模式   → ai-component-standardizer → 加入禁止模式清单
项目约定         → ai-component-standardizer → 更新模板
架构映射         → ai-architect-governor     → ADR
库清单           → ai-library-first          → 更新库目录
```

```markdown
### 回滚方案
- [每一批出问题时如何撤销]
- [数据库备份策略]
- [进入下一批之前必须通过哪些测试]
```

### 阶段 5：EXECUTE — 外科手术式修改 | Surgical Changes

**修改存量代码的规则：**

| # | 规则 | 理由 |
|---|---|---|
| 1 | **匹配既有风格，即使你并不认同** | 一致性 > 风格偏好上的正确性 |
| 2 | **一次提交只做一类改动** | 重构或功能，禁止在一次提交里同时做 |
| 3 | **改行为之前先补测试** | 测试是重构的安全网 |
| 4 | **保持系统可运行** | 禁止弄坏主干；使用功能分支 |
| 5 | **没坏就别修** | 如果它能用且不在范围内，就不要碰 |
| 6 | **数据库改动要格外谨慎** | 备份 + 空跑 + 回滚脚本 + 验证 |
| 7 | **接口稳定优先于内部美观** | 公开 API 保持兼容；只重构内部 |

### 分级执行规则 | Level-Specific Execution Rules

| 级别 | 执行规则 |
|---|---|
| 1（快速修复） | 只读受影响文件 + 直接依赖。完全照抄既有风格。 |
| 2（功能追加） | 照抄 2-3 个同类模块。结构、命名、模式保持一致。 |
| 3（模块升级） | 测试先行。重构内部。保持公开 API。一次一个模块。 |
| 4（深度改造） | 全面审计 → 每项改动一份 ADR → 增量批次 → 保持系统可运行。 |
| 5（接管） | 先记录真实状态。按依赖排序。在基础功能跑通之前不谈"锦上添花"。 |

## 4. 半成品/接手项目 | Semi-Finished / Takeover Projects

### 接手项目中的危险信号 | Red Flags in Takeover Projects
| 危险信号 | 应对 |
|---|---|
| 没有 README 或文档 | 在审计阶段（阶段 1）自己写一份 |
| 没有测试 | 做任何改动之前先补冒烟测试 |
| 语言/框架混用 | 记录哪里用什么；不要再加新的 |
| 死代码 / 被注释掉的代码块 | 在审计中记下，只在专门的清理批次里删除 |
| "它基本能跑" 这类说法 | 每一条说法都独立验证；只相信你亲眼看到能跑起来的东西 |
| 没有数据库迁移脚本 | 做任何 DB 改动之前先手工把 Schema 记录下来 |

### 接管审计模板 | Takeover Audit Template
```markdown
## 接管审计：[Project Name]

### 能用的部分（跑起来验证过的）
| 功能 | 状态 | 备注 |
|---|---|---|
| 用户登录 | ✅ 可用 | |
| 看板 | ⚠️ 部分可用 | 5 个部件中 3 个能渲染 |
| 报表导出 | ❌ 已损坏 | 500 错误 |

### 缺失的部分（未实现）
| 功能 | 优先级 | 依赖 |
|---|---|---|
| 邮件通知 | P1 | SMTP 配置 |
| 移动端自适应 | P2 | CSS 重构 |

### 有缺陷的部分
| 缺陷 | 严重级 | 复现步骤 |
|---|---|---|
| 日期选择器时区显示错误 | P1 | 选择日期，观察 UTC 偏移 |

### 收尾顺序（基于依赖，而不是愿望清单）
1. 修复严重缺陷（P0）
2. 补完部分可用的功能
3. 补齐缺失的必备功能
4. 为以上全部补测试
5. 最后才轮到锦上添花的功能
```

## 5. 常见陷阱（来自 GERP 实战经验）| Common Brownfield Traps (from GERP Experience)

| 陷阱 | 会发生什么 | 预防 |
|---|---|---|
| **"干脆重写吧"** | 6 个月后，新版本带着另一批缺陷，而老版本还在跑 | 禁止重写；增量改造 |
| **"都到这儿了，顺手一起修"** | 一次缺陷修复变成 3 天重构，带出 5 个副作用 | 外科手术式聚焦：只修范围内的东西 |
| **强加新模式** | 团队用模式 A 已经 2 年；AI 强推模式 B → 不一致的混乱 | 提炼既有模式，不强加新模式 |
| **跳过审计** | 立刻开始写代码 → 弄坏了某处"看起来不对"但其实是故意为之的逻辑 | 审计先行，永远如此 |
| **不检查既有库就加新库** | 项目已经在用 Chart.js；AI"因为它更好"又加 ECharts → 体积膨胀 | 查 ai-library-first，尊重既有选择 |
| **只测新代码** | 新功能正常；老功能崩了 → 回归 | 每次改动都做完整回归测试 |

## 5b. 其他未考虑场景 | Additional Brownfield Scenarios

### 场景：原始团队不在 | Scenario: Original Team Unavailable

**征兆**：没有人知道某些决策为什么这么定。"一直都是这样的。"

```
处理"没有原始团队"的项目：

1. 把代码当作唯一文档
   - 注释可能已过期。代码才是真相。
   - git blame 是你最好的历史学家（谁在何时改了什么）

2. 从代码反向还原业务规则
   - "为什么折扣上限是 15%？" → 找到那个常量/方法
   - 不要猜。答案就在代码的某个地方。

3. 理解一点，就补一个测试
   - 每当你搞清楚"这段在做什么"，就补一个测试
   - 测试会成为下一位开发者的新文档

4. 不要臆测意图
   - "这看起来不对" ≠ "这确实不对"
   - 它可能是针对某个已不存在的条件的绕过方案
   - 也可能是出于你尚未发现的某个原因而故意为之

5. 建一份「BUS FACTOR」文档
   - 哪些模块已经没有任何存活的知识？
   - 优先记录这些模块
```

### 场景：需要数据迁移 | Scenario: Data Migration Required

**适用**：旧系统里有活数据，必须迁到新系统/升级后的系统。

```
数据迁移检查清单：

[ ] 先审计源数据质量
    - 有空值吗？有重复吗？格式不一致吗？
    - 在源端修复，而不是迁移之后再修

[ ] 建立 旧 Schema → 新 Schema 的映射
    - 每张表一份映射文档
    - 标注：直接映射 / 需要转换 / 无法迁移

[ ] 编写迁移脚本
    - 幂等（可以安全地重复执行）
    - 具备 dry-run 模式
    - 逐行记录每一处变更

[ ] 在生产数据的副本上测试
    - 禁止在实时数据上测试迁移
    - 核对行数是否一致（源 vs 目标）

[ ] 制定回滚方案
    - 如果迁移中途失败，如何恢复？
    - 备份 + 事务 + 检查点策略

[ ] 安排迁移窗口
    - 选流量最低的时段
    - 全程开启监控
    - 回滚小组待命
```

### 场景：环境不一致 | Scenario: Environment Drift

**适用**："在我机器上是好的"，但到预发/生产就失败。配置文件已经漂移。

```
环境漂移审计：

[ ] 跨环境比对配置
    diff dev/application.yml staging/application.yml
    diff staging/application.yml prod/application.yml

[ ] 检查：
    - 依赖版本不一致（package.json vs package-lock.json）
    - Node/Java/Python 版本不一致
    - 数据库版本不一致
    - 只在某一台机器上存在的硬编码路径
    - 手工设置的环境变量（不在配置里）

[ ] 统一化：
    - 一份配置模板 + 各环境覆盖项
    - 用 Docker 保证环境一致
    - .env.example 入库，.env 加入 git-ignore

[ ] 验证：
    - 全新克隆 → 一条命令即可在本地跑起来
    - README 必须写明精确的搭建步骤
    - 如果搭建耗时 > 10 分钟，说明有问题
```

### 场景：何时放弃重做 | Scenario: When to Walk Away

有时候最负责任的做法，是承认这个项目需要从零开始。

```
决策标准：重建（Rebuild）还是改造（Renovate）

| 因素 | 权重 | 打分 1-5 |
|---|---|---|
| 存在且能通过的测试 | 20% | [SCORE] |
| 依赖是当前版本（< 12 个月） | 15% | [SCORE] |
| 架构是连贯的（不是补丁拼凑） | 20% | [SCORE] |
| 团队理解这套代码库 | 15% | [SCORE] |
| 核心功能工作正常 | 20% | [SCORE] |
| 满足安全基线 | 10% | [SCORE] |

加权得分 < 2.5 → 强烈建议重建
加权得分 2.5-3.5 → 谨慎改造
加权得分 > 3.5 → 改造（项目仍可挽救）
```

**重建规则**：
- 先从旧系统提炼出全部业务规则（它们才是真正的资产）
- 尽可能保留数据库 Schema（数据 > 代码）
- 增量重建，在新系统被验证之前保持旧系统运行
- 这不是新项目（greenfield）——你带着业务规则一起走
