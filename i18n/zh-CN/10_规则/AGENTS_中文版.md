## 0. 会话启动协议 | Session Start Protocol (EVERY SESSION)

### 0.0 正式源目录 | Source of Truth

**正式可移植方法论源（Official portable methodology source）：**
- Skills：`skills/`
- Skill manifest：`skills/SKILL_MANIFEST.json`
- Rules：`AGENTS.md` 与 `rules/AGENTS.md`
- 工具适配器目录（Tool adapter folders）：`.agents/`、`.trae/`、`.qoder/`、`.claude/`、`.codebuddy/`
- 私有本地归档（private local archive）被排除在发布包之外，且永远不作为正式 Skill 根目录。

当某条规则提到某个 Skill 时，先从 `skills/{layer}/{skill-name}/SKILL.md` 解析。适配器目录可能由 `tools/deploy.ps1` 生成，不得当作唯一真相源。

### 0.1 防遗忘 | Task Continuity
**在做任何其他事情之前：**
1. 读取 `docs/全项目总控/TASK_BACKLOG.md`
2. 若存在未完成任务 → 提醒用户：
   "You have [N] unfinished tasks: [list]. Continue or start new?"（你有 [N] 个未完成任务：[清单]。继续，还是开始新任务？）
3. 用户决定 → 更新待办台账（backlog）


### 0.2 工具发现 | Tool Discovery (Brownfield projects)
**在分析老项目（brownfield，存量项目）之前：**
1. 运行：`py scripts/py/discover_tools.py {project_path} --by-purpose`
2. 按用途清点现有脚本
3. 使用现有脚本，不要另写新脚本
4. 匹配项目既有模式

**规则**：若一个项目有 50+ 个脚本，说明它的工具链已经成熟。尊重它。

### 0.3 环境自检 | Environment Verification
**在进行任何代码工作之前：**
1. 运行：`py scripts/py/env_check.py --quick`（Linux/Mac 上使用 `python` 或 `python3`）
2. 若工具缺失 → 交给 ai-tool-bootstrapper 自动安装
3. 若工具齐备 → 继续

**当真正的问题是缺少某个工具时，绝不要浪费时间调试"神秘错误"。先检查环境。**

### 0.4 路径记忆 | Tool Path Check
**在安装任何工具之前：**
1. 检查 `tools/tool-registry.json` —— 该工具是否已经安装？
2. 运行：`py scripts/py/tool_registry.py get {tool_name}`
3. 若已登记 → 使用现有路径。禁止重复安装。
4. 若为新安装 → 登记路径：`py scripts/py/tool_registry.py set {name} "{path}" "{version}"`

### 0.5 5S 交付接管 | 5S Delivery Takeover

对于版本化交付、共享能力、发布、部署、Schema、权限或支持基线（supported baseline）缺陷（Bug）类工作：

1. 读取 `skills/core/ai-5s-delivery-governor/SKILL.md`。
2. 记录最小充分变更记录：类型、目标版本/产线、受影响流程、真相责任人（truth owner）、非目标（non-goals）与 L0-L3 门禁（gate，即 L0/L1/L2/L3）。
3. 基线 Bug 按"在哪里复现"路由（Bug routing），而不是按"在哪里发现"路由。
4. 不得把一次本地修改或一次本地提交称为已交付。必要的集成、远端（remotes）、CI、发布与部署证据，仍是项目自有的收口条件。

使用轻量生命周期：`Scope -> Specify -> Ship -> Safeguard -> Sell`，即范围（Scope）→ 说明（Specify）→ 实现（Ship）→ 保障（Safeguard）→ 销售放行（Sell）。对只读审计、草稿或小型本地实验，不得强加发布仪式。

### 0.6 产品主导的全 AI 交付 | Product-Directed AI Delivery

对于产品主导（product-led）交付，product owner 可以完全使用业务语言、截图、示例和已完成的业务流程测试来工作。product owner 拥有结果、可用性、范围、优先级、非目标与最终业务验收（business acceptance）。AI 智能体拥有需求分析、对标调研、架构、Schema、后端、前端、测试、证据与发布执行。

在实现任何可复用功能之前，必须先声明两条链：

```text
Backend: truth -> atomic service -> orchestration -> aggregate interface -> command gateway -> adapters -> Host
Frontend: runtime/field truth -> UI atom -> UI orchestration -> standard template -> Host page
```

两条链的中文对照：后端 = 真相 → 原子服务（atomic service）→ 原子编排（atomic orchestration）→ 聚合接口（aggregate interface）→ 命令网关（command gateway）→ 适配器（adapter）→ Host；前端 = 运行时/字段真相 → UI 原子（ui atom）→ UI 编排（UI orchestration）→ 标准模板（standard template）→ Host 页面（host page）。

Host 页面（host page）与传输适配器只负责加载、渲染、收集输入、请求受支持的命令并展示反馈。它们禁止成为业务逻辑、状态流转、字段真相（field truth）、授权、计算或写入路径的第二来源。技术门禁通过，不能替代 product owner 已完成的业务流程验收（business-flow acceptance）。

产品归属、智能体交接（handoff）、十二步交付地图与验收边界，见 `skills/core/ai-product-directed-delivery/SKILL.md`。

### 0.7 安全修改与精准定位 | Safe AI Change and Code Location

对于任何 Bug 修复、功能、重构、删除、重命名、迁移或大型项目批次，写代码之前先使用 `skills/core/ai-product-directed-delivery/SKILL.md`。

以下是安全修改（safe change）与代码定位（code location）的五条要求：

1. **Read, prove, then change（先读、先证、再改）**：识别业务症状、真相责任人、候选文件、既有工作区（working-tree）改动、影响（impact）边界、验证方式与回滚路径。
2. **从用户流程回溯到真相**：`menu/route -> rendered Host -> shared UI/template -> API -> controller/adapter -> command gateway/aggregate -> orchestration/atomic service -> domain facts/FieldPackage/BusinessProfile/permission -> mapper/DB -> tests/gates`。
3. **保护文件与代码**：对删除/重命名/批量替换进行分级。共享文件、未知文件、Schema、配置、租户数据以及破坏性（destructive）Git 操作默认保留；数据库级或全仓库级的破坏性（destructive）操作必须显式确认并提供恢复证据。
4. **保持无关工作不动**：禁止全局清理脏工作区；按文件或按块精确暂存（exact file or hunk staging），检查已暂存的 diff，并在提交前验证它。只暂存任务自有精确改动（exact task-owned）。
5. **大规模工作以自动驾驶批次（autopilot batch）运行**：AI 绘制代码与依赖关系、选择 L0-L3 门禁、逐批实现并证明，然后汇报产品可见结果，只在业务歧义（business ambiguity）、重大权衡、破坏性（destructive）决策或发布授权上询问负责人。

product owner 永远不需要定位源文件或写代码。AI 拥有调查与实现；负责人拥有产品意图与业务流程验收（business-flow acceptance）。

### 0.8 职责、任务包与方法论回归 | Delivery Roles, Task Pack, and Methodology Regression

对于产品主导或多步骤交付：

1. 读取 `docs/全项目总控/AI_DELIVERY_SKILL_RESPONSIBILITY_MATRIX.md`，为当前阶段选定一个主责 Skill。
2. 从 `docs/_templates/全项目总控/AI_PRODUCT_DELIVERY_TASK_TEMPLATE.md` 开始。product owner 只提供产品结果、示例、优先级、可用性期望与业务流程验收（business-flow acceptance）；AI 填写工程证据。
3. 当正式规则、产品交付 Skill、模板或路由边界发生变化时，除 `audit_methodology.py` 之外，还要运行 `py scripts/py/test_methodology_scenarios.py --project-root .`。

责任矩阵只澄清归属；它不授权任何 Skill 绕过项目专属规则、真相责任人、验证门禁或显式的破坏性（destructive）操作确认。

### 0.9 新鲜证据、共享语言与双轴审查 | Evidence Freshness, Shared Language, and Two-Axis Review

对于非平凡交付：

1. **Fresh evidence before claims（先给新鲜证据再下结论）**：先确定能够证明结论的命令、浏览器检查、API 调用、数据库回读（readback）或 diff 检查；在最后一次相关改动之后运行它；在看到其退出状态与结果之后，才可以说任务完成、已修复、通过或可提交/发布。更早的证据、一个绿色的健康端点，或仅有智能体报告，都不构成收口。
2. **关键接缝测试先行**：对新增或变更的领域规则、Bug 回归、命令/编排行为以及其他可测试的公共接口，先写一个针对目标行为失败的重点测试，再实现最小的通过改动，并重跑该重点测试与受影响的回归测试。禁止把红绿（red-green）流程强加到仅复制、生成物、仅配置或探索性任务上；改为记录有理由的验证方式。
3. **共享语言（shared language）是交付资产**：当任务引入或依赖有歧义的领域术语、稳定缩写或跨会话决策时，在 `docs/` 下维护一份简洁的项目上下文/术语表以及 ADR 或决策记录。在规格、测试、API 与代码中复用这套语言；不得让术语表取代权威业务规则或数据模型。
4. **Review two independent axes（独立审查两轴）**：对非平凡改动，在提交或发布前同时审查（a）标准/真相/架构/质量门禁，以及（b）原始产品结果、验收流程与显式非目标。只有当两条轴都不存在未处理的阻断项时，改动才算通过审查。该审查的力度与所选 L0-L3 门禁相称，并优先复用项目既有的审查工具。

对于发布或客户可交付（customer-readiness）结论，还要记录由 `ai-5s-delivery-governor` 给出的、实际达成的 `Q0-Q3` 交付资格（qualification）与可销售性（saleability）。`Q0` 仅表示能力存在；`Q1` 表示基线对齐；`Q2` 表示技术上可执行的后端收口；`Q3` 表示真实业务验收、对账（reconciliation）与发布证据。HTTP 200、健康检查、页面可用、CI 与本地提交，永远不能把结果提升到 `Q3`。

### 0.10 可执行交付契约 | Executable Delivery Contract

对于 L2/L3 交付、并行智能体工作，或任何带有破坏性（destructive）、跨模块、权限、Schema、发布或高风险边界的工作：

1. 读取 `skills/core/ai-delivery-contract-governor/SKILL.md`。
2. 以 `docs/_templates/全项目总控/task_contract.json` 为模板，依据 `docs/全项目总控/schemas/governance/delivery-contract.schema.json`，创建任务本地的 `DeliveryContract`。
3. 在写入之前，用 `py scripts/py/validate_delivery_contract.py --contract <path>` 校验范围、真相责任人、非目标、公共测试接缝（public test seam）或有理由的替代方案、证明计划（proof plan）与精确写入白名单（write allowlist）。
4. 在保障（Safeguard）/完成（complete）之前，校验实际变更文件、新鲜最终证据与独立的双轴审查。L2/L3 要求 `verification_owner` 与 `implementer` 不是同一人。

契约是失败即阻断（fail-closed）的：白名单之外的变更路径、显式禁止的路径、缺失证明、过期证据（stale evidence）或失败/待定的审查，都会阻断 `safeguarded` 与 `completed`（状态置为 `blocked`）。它不替代项目自有的测试、运行时/数据库证据、CI、业务真相或负责人授权。

对于数据库、种子数据、参数基线或租户数据变更，契约必须关联一条迁移一致性记录，覆盖 manifest 标识、校验和（checksum）、测试/生产登记、执行历史、迁移后检查与恢复。对于租户生命周期变更，契约必须关联一条回归记录，覆盖目标/对照租户、写入范围、隔离性、权威回读（authoritative readback）、审计与残留或回滚检查。能力声明必须写明其成熟度：`registered -> configured -> authorized -> provider-covered -> runtime-executable -> business-closed`（已登记 → 已配置 → 已授权 → 提供方覆盖 → 运行时可执行 → 业务闭环）。

## 1. 概述 | Overview

本文档定义了 AI 辅助企业级软件开发的强制性规则、工作流和工程纪律。它来自一个真实多租户 ERP 系统上经过实战检验的实践，并已通用化为适用于任何项目。

### 核心哲学 | Core Philosophy

| 原则 | EN | CN |
|---|---|---|
| **Check Before Execute** | Never assume. Always verify the current state of DB, code, runtime before acting. | 先检查后执行：任何操作前必须核实数据库、代码、运行时现状 |
| **No Degradation** | Find root cause. Never apply temporary workarounds. | 禁止降级方案：必须找到根本原因，不允许临时绕过 |
| **Data-Driven Development** | DB is the single source of truth. All changes start from the database. | 数据驱动开发：数据库是唯一真相源，所有修改从数据库开始 |
| **Frontend = Display Only** | Frontend renders. Backend decides. Zero business logic in UI layer. | 前端纯展示：前端绝不写业务逻辑、计算、校验、决策 |
| **Library First** | Never rewrite what a mature open-source library already does. | 库优先：优先使用成熟开源组件，禁止重复造轮子 |
| **Zero-Fluff UI** | ERP/SaaS/admin pages must have zero decorative text. Only actionable prompts. | 零废话规则：管理后台页面禁用装饰性文案，只保留可操作提示 |
| **Plan-Driven Execution** | Every task must have a plan with acceptance criteria before execution. | 计划驱动：每个任务必须先制定详细计划再执行 |
| **Long-Term Collaboration** | Treat AI-assisted enterprise delivery as sustained cooperation, not a one-shot token burn. | 长期协作：默认服务长期 ERP/企业级交付，不把成本压力误判为“用户用不起”，而要通过拆批、验证和复用降低消耗 |
| **5S Delivery Governance** | Bound delivery through Scope, Specify, Ship, Safeguard, Sell. | 5S 交付治理：用范围、说明、实现、保障、销售放行约束可审计交付。 |
| **Product-Directed AI Delivery** | Product owner defines outcome and acceptance; AI agents execute the verifiable engineering system. | 产品主导全 AI 交付：人定义结果与验收，智能体完成可验证工程系统。 |

### 协作成本护栏 | Collaboration Cost Guardrail

- 方法论是长期交付资产。当更小的已验证批次就能解决当前业务问题时，不要强迫每个任务都走完整 OS 路径。
- 为长期协作而优化：优先使用有边界的批次、可复用脚本、既有工具和基于证据的验证，而不是反复的大范围探索。
- 绝不要仅仅为了省 token 或省时间，就跳过必需的验证、数据库检查、构建检查、API 检查、浏览器检查或 git 范围检查。
- 当一个平台级构想对一个人或一个交付周期来说过大时，把它保留为私有能力、规则或未来路线图项，并优先处理能保住当前现金流与交付势头的 ERP/业务任务。
- 在公开/开源定位上，区分厚重的内部内核与轻量的采用入口。先讲审计、轻量安装、验证和具体证据，再呈现完整的 AI 开发操作系统。

## 3. 强制开发顺序 | Mandatory Development Order (13+1 Steps)

### 步骤 0：项目分类 | Step 0: Project Classification
- 在 4 个维度上对项目分类
- 选定 Skill 集与架构原型（archetype）
- **门禁（Gate）**：分类已记录在案

### 后端阶段 | Backend Phase

| 步骤 | 动作 | 验证 |
|---|---|---|
| 1 | **数据库初始化（Database Init）** —— SQL 脚本 → 建 Schema → 校验表 | SHOW TABLES; DESCRIBE table; |
| 2 | **实体层（Entity Layer）** —— 生成实体类 → 补注释 → 校验映射 | 检查字段-列对齐 |
| 3 | **Mapper 层（Mapper Layer）** —— 继承 BaseMapper → 自定义查询 → 校验 SQL | 执行并检查结果 |
| 4 | **服务层（Service Layer）** —— 业务逻辑 → 缓存配置 → 事务管理 | 单元测试通过 |
| 5 | **控制器层（Controller Layer）** —— REST API → API 文档 → 权限控制 | curl 端点测试 |
| 6 | **构建验证（Build Verification）** —— 编译 → 启动测试 → API 健康检查 | 健康端点 UP |

### 前端阶段 | Frontend Phase

| 步骤 | 动作 | 验证 |
|---|---|---|
| 7 | **API 契约（API Contracts）** —— 由后端生成 → 校验字段一致性 | 与后端 DTO 比对 |
| 8 | **服务层（Service Layer）** —— API 调用封装 → 错误处理 → 校验端点 | Network 面板检查 |
| 9 | **组件（Components）** —— 页面开发 → 复用标准模板 → 功能测试 | 遵循 component-standardizer |
| 10 | **集成测试（Integration Test）** —— API 测试 → 功能完备性 → 错误处理 | 全流程测试 |
| 11 | **种子数据（Seed Data）** —— 写测试数据 → 在 DB 中校验 → 在 UI 中验证 | CRUD + 边界用例 |
| 12 | **Schema 同步（Schema Sync）** —— 模板 → 全部实例 → 校验同步状态 | 比对 Schema |

### 验证阶段 | Verification Phase

| 步骤 | 动作 | 验证 |
|---|---|---|
| 13 | **运行时验证（Runtime Verify）** —— 无头浏览器 → 检查 console/loading/DOM/API | ai-runtime-verify 返回 passed:true |
| 13a | **发布治理（Release Governance）**（仅企业级）—— 锁版（Lock-version）、P0 审计、手工测试台账、业务流程验收 | 全部 P0=0，P1<5，手工测试通过 |

**⚠️ 关键**：在宣布"开发完成"之前，步骤 13 必须通过。对企业级发布，步骤 13a 是强制的（MANDATORY）。

**⚠️ 关键**：在宣布"开发完成"之前，步骤 13 必须通过。见 `skills/governance/ai-runtime-verify/SKILL.md`

**关键规则**：每一步必须先通过验证，才能进入下一步。

## 5. Skill 加载生命周期 | Skill Loading Lifecycle

### ⚠️ 上下文衰减警告 | Context Decay Warning
AI 上下文窗口是有限的。在长会话早期加载的规则会从活跃记忆中衰减。这不是缺陷 —— 而是物理限制。下面的加载生命周期就是为了对抗这一点。

- `skills/core/ai-tool-bootstrapper/SKILL.md`

### 阶段 2：领域进入（进入新领域时加载）| Phase 2: Domain Entry (Load When Entering New Domain)

### 阶段 3：门禁前重读（关键动作前加载）| Phase 3: Pre-Gate Re-Read (Load Before Critical Actions)

### 阶段 4：压缩规则提醒 | Phase 4: Compressed Rule Reminder
当上下文紧张、完整重读 Skill 代价过高时，使用这份压缩清单：

```
QUICK CHECK (15 rules, always active):
□ Frontend = display only. Backend computes everything.
□ Check ai-library-first before writing custom code.
□ Page must match standard template (list/document/report/dashboard).
□ Notification severity: P0=Modal, P1=Banner, P2=Toast, P3=Console.
□ Test evidence REQUIRED before "done" — must show verify JSON path or test output.
□ Missing tool → auto-install, never ask user.
□ Every page handles 4 states: loading, empty, error, edge.
□ Brownfield: audit before code, match existing style.
□ No business logic in Vue computed() or React useMemo().
□ Single truth: never compute same value in two places.
□ Versioned delivery: record 5S state and select an L0-L3 gate.
□ Product owner owns business acceptance; AI owns evidence-backed engineering execution.
□ Completion claims use fresh evidence from the final relevant change.
□ Critical business seams use focused red-green tests when testable.
□ Review both standards/truth and the originating business acceptance.
```

上列 15 条的中文对照（代码块本身按原文保留，未作改写）：
1. 前端 = 纯展示。后端计算一切。
2. 写自定义代码前先查 ai-library-first。
3. 页面必须匹配标准模板（资料列表/单据/报表/看板）。
4. 通知分级：P0=模态框、P1=横幅、P2=轻提示（Toast）、P3=控制台。
5. "完成"之前必须有测试证据 —— 必须给出 verify JSON 路径或测试输出。
6. 缺工具 → 自动安装，绝不询问用户。
7. 每个页面处理 4 态：加载、空、错误、边界。
8. 老项目（brownfield）：先审计再写代码，匹配既有风格。
9. Vue computed() 或 React useMemo() 中禁止业务逻辑。
10. 单一真相：同一取值禁止在两处各算一次。
11. 版本化交付：记录 5S 状态并选择 L0-L3 门禁。
12. product owner 拥有业务验收；AI 拥有有证据支撑的工程执行。
13. 完成声明必须使用来自最后一次相关改动的新鲜证据（fresh evidence）。
14. 关键业务接缝在可测试时应使用聚焦的红绿（red-green）测试。
15. 同时审查标准/真相与原始业务验收。

## 11. PDCA 执行循环 | PDCA Execution Cycle

`
PLAN  -> Task analysis, decomposition into safe batches
DO    -> Execute step by step, record evidence
CHECK -> Verify each step result against acceptance criteria
ACT   -> Extract lessons, update skills, close the loop
`

循环各阶段对照：
- PLAN（计划）→ 任务分析，拆解为安全的批次
- DO（执行）→ 逐步执行，记录证据
- CHECK（检查）→ 按验收标准校验每一步结果
- ACT（处理）→ 提炼经验，更新 Skill，闭环

## 12. 新项目初始化 | Project Bootstrapping

对新项目，按以下步骤初始化方法论：

1. **先分类** —— 用 ai-project-classifier（Step 0）判定原型（A/B/C）
2. **搭建目录** —— 创建与你的原型匹配的项目结构。见 `methodology/08_项目文件夹结构标准.md`
3. 把 `rules/AGENTS.md` 复制到项目根目录
4. 把 `skills/core/` 与 `skills/governance/` 复制到 `{project}/skills/`
5. 按你的技术栈挑选相关的 `skills/tech/`
6. 把 `docs/_templates/` 复制到 `{project}/docs/`
7. 按文档体系创建 docs 子目录
8. 运行 ai-rule-dispatcher 执行首次项目审计
9. 运行 ai-tool-bootstrapper 校验全部工具依赖
10. **部署到 AI 工具** —— 运行 `tools/deploy.ps1` -Tool all -Force，把 Skill 软链接、把规则复制到所有受支持的工具（Codex、Trae、Qoder、CodeBuddy、Claude、Cursor、Copilot、Windsurf、Lingma）
11. 在声称方法论包干净之前，运行 `py scripts/py/audit_methodology.py --project-root .`

**从第一天起强制执行的目录规则**：
- 项目根目录：只允许 AGENTS.md + .editorconfig + 构建文件
- database/：migrations/ + seed/ + schema/ —— 不允许零散 SQL 文件
- docs/：类型优先的层级 —— 根目录不允许零散 .md 文件
- scripts/：bat/ + ps1/ + py/ + js/ + ci/
