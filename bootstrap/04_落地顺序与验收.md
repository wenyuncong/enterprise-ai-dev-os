# 落地顺序与验收 | Rollout Order and Acceptance

> **原则**：先提取（不改行为）→ 再生成（可复现）→ 后适配（可替换）→ 最后验证（两个样本）。
> **每个阶段都必须可回滚**，且不得让母版进入不可交付状态。

---

## P1 提取与参数化（母版 → 模板）

| 交付物 | 内容 | 来源 |
|---|---|---|
| 5S 脚本族模板 | 9 个脚本参数化：分支模型、远端列表、`ChangeType`、`Gate`、关闭判据 | 母版 `scripts/ps1/*5s*.ps1` |
| git hooks 模板 | `.githooks/{commit-msg,pre-commit,pre-merge-commit,pre-push}` | 母版 `.githooks/` |
| 门禁骨架 | `scripts/ci/` 的 check 脚本骨架 + 自测目录 + 薄启动器 | 母版 `scripts/ci/` |
| 知识中心生成器 | MD→HTML + 子站 + 架构图册 + `--check` | 母版 `scripts/py/generate_*` |
| 交付模板包（去领域化） | 9 件实施交付模板 | 母版 `docs/实施交付模板包/` |

**验收（硬标准）**：把参数化后的 5S 脚本**在母版上原样跑一遍**，输出必须与母版原脚本**逐字一致**（同一 commit、同一分支、同样参数）。任何不一致都视为提取失败。

**回滚**：本阶段只新增模板文件，母版不做任何替换，因此回滚 = 删除新增目录。

## P2 机读三件套 + 生成器

| 交付物 | 内容 |
|---|---|
| 三份 Schema | `project-profile` / `task-routing` / `gates`（本目录 `02_机读三件套/`） |
| 母版填充示例 | 用真实内容填好的三份 JSON（同一目录 `examples/gerp/`） |
| 校验器 | `validate.py`（无 jsonschema 时退化为轻量结构校验） |
| `methodology init` | 一条命令生成 8 类产物（规则入口 + 三件套 + 门禁骨架 + 5S + 知识骨架 + 知识中心 + 证据链 + 首次自检） |

**验收（硬标准）**：在**空目录**执行 `methodology init`，30 分钟内达到"受控状态"：

1. `G-5S-ENTER` 类接管脚本可跑并给出明确结论；
2. `gates.json` 至少 1 条静态门禁可执行并留下证据文件；
3. `knowledge --action build` 生成知识中心，`--action check` 返回一致；
4. `route` 对 3 个样例任务返回正确的 `risk_level` 与 `load`；
5. 首次 commit 成功，`.githooks` 生效（故意违反一次，必须被拦下）。

**回滚**：生成的产物都在新目录内，删除即回滚；生成器本身无副作用。

## P3 DSH 适配

| 交付物 | 内容 |
|---|---|
| 5 个 CLI 工具 | `route` / `precheck` / `gate` / `sync` / `knowledge` |
| MCP 面 | 同一实现的第二个面（CLI 先行，MCP 后接） |
| 裁剪规则 + profile | 按 archetype/角色的技能投放；`methodology-*` profile |
| 钩子结论 | ⚠️ DSH 写前钩子的实测结论（支持与否决定强强制落点） |

**验收（硬标准）**：

1. 5 个工具在**母版上只读运行**，`gate` 结果与母版现有脚本一致；
2. 投放技能数满足裁剪上限（A ≤ 6，B ≤ 20，C 按角色 ≤ 12）；
3. 会话启动加载量 **≤ 5 KB**（实测，不含模型自身 system prompt）；
4. 故意越界任务被 `precheck` 或 CI 拦下，且给出可执行的修法；
5. 至少 3 家模型跑完 M0–M3，产出一张适配矩阵。

**回滚**：DSH 侧只新增 `data/profiles/*`（必要时 `data/skills/*`），删除即恢复原状；**不改 DSH 本体**（它是 npm 包，`upgrade-dsh.ps1` 会覆盖）。

## P4 双样本验证

| 样本 | 目的 | 验收 |
|---|---|---|
| 一个新项目（greenfield，archetype B） | 验证"从零到受控" | `methodology init` 后 30 分钟进入受控状态（同 P2 验收） |
| 一个老项目（brownfield，archetype C） | 验证"改造路径" | 只读审计产出风险地图 + 分批计划；**不启动全仓重构** |
| 母版（作为回归参照） | 验证"提取没改变行为" | 同一 commit 下，模板脚本与母版脚本输出一致 |

## PROVENANCE 规则（每个通用件都要有）

每个从母版提取的件，必须在文件头或清单里记录三件事：

```text
PROVENANCE
  source      : 母版项目内相对路径（不写本机绝对路径）
  original_use: 原本解决什么问题
  extracted_at: 提取日期 + 母版提交号
```

理由：半年后要判断"这个门禁能不能删"，唯一可靠的依据是它当初挡住了什么。

## 护栏（五条硬约束）

| # | 护栏 | 违反后果 |
|---|---|---|
| 1 | 模板**只带机制，不带领域事实** | 会把母版业务语义污染到别的项目 |
| 2 | 生成后**项目内副本是真相**，模板只是生成器 | 出现第二真相源，AI 路由漂移 |
| 3 | 每个通用件必须有 PROVENANCE | 无法判断门禁是否还有效，只能全留或全删 |
| 4 | **别做万能配置**——先支持 archetype A/B/C，其余拒绝 | 配置组合爆炸，没人敢改模板 |
| 5 | 适配验收用 **M0–M3**，不用"感觉" | "国产模型行不行"永远吵不清 |

## 第一个可验证目标（建议）

**在母版上只读跑一次 `gate`，结果与母版现有脚本完全一致。**

- 成本：低（母版脚本已存在，只需一个统一入口）；
- 收益：立刻证明"模板化的门禁没有改变行为"，这是后面所有阶段的地基；
- 风险：零（只读，不改母版一行）。
