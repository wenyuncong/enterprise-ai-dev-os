# 项目模板引导层 | Project Bootstrap Layer

> **本目录是什么**：把「母版项目」里已经验证过的机制，抽象成**可实例化的项目模板**与**机读清单**，让一个新项目（或一个老项目）在 30 分钟内进入受控状态。
> **文档语言**：中文优先（标识符、命令、路径、枚举值保持英文）。
> **状态**：设计层产出。**未修改任何被参照项目的一行代码**，只做只读盘点与抽象。

---

## 1. 四个角色的关系（先对齐定位，否则会做重）

```text
母版（Reference Implementation）
  母版 ERP 项目：机制已在生产验证，同时携带领域事实
        │  只提炼「机制」，不带「领域事实」
        ▼
提炼层（本仓库 = 方法论）
  rules / skills / methodology / docs/_templates / bootstrap（本目录）
        │  生成
        ▼
模板（Template）
  archetype A / B / C 三类项目骨架 + 机读三件套
        │  实例化
        ▼
实例（Project Instance）
  新项目或改造中的老项目；项目内副本是唯一真相
        │  执行
        ▼
引擎（Engine，可替换）
  DSH（Code Harness）为第一实现；其它 runtime 通过 MCP 契约接入
```

**三条不可违反的分界**：
1. **模板只带机制，不带领域事实**——否则会把母版的业务语义污染到别的项目。
2. **生成后，项目内副本是真相，模板只是生成器**——模板不得成为第二真相源。
3. **引擎可替换**——业务真相与门禁归项目，执行能力由引擎提供；换引擎不得动业务。

## 3. 为什么"自动加载"必须先把规则变成机读

散文规则无法被自动加载，只能靠模型读散文去猜。母版现在是**半机读**状态——风险分级表、任务类型映射表都已经存在，但散在 30 KB 级的规则文件里（母版的 `project_rules.md` 单体已达 **97.7 KB / 1589 行**，且存在编号重复）。因此本层的做法是：

1. 抽出三份机读文件（`project-profile` / `task-routing` / `gates`）；
2. 散文规则**降级为解释层**，只在对不上时查阅；
3. 加载按三级走：会话启动（≤5 KB）→ 任务路由切片 → 门禁执行。

这与母版既有的 `L0–L3 风险等级 → 规则加载策略` 完全一致，只是把"人读表格"变成"机读清单"。

## 4. 与中文版（i18n）的关系

`i18n/zh-CN/` 是**人读对照层**；本目录是**机器与生成器用的规格层**。两者不重复：本目录的文字在人读时可直接看中文，但它的主要消费者是 `methodology init` 生成器与门禁脚本。等本层稳定后，再决定是否镜像进 `i18n/zh-CN/`。
